# Spike — the Unreal test runtime: masters on Epic's OpenPBR, headless capture, a standalone package

**Run:** 2026-09-29, on the UE machine (Unreal 5.8.0, RTX 4090, Linux). **Mnemonic:** `UR` (continues `260929_R_UnrealTestRuntimeHere.md`; ids `UR-F4` on). **Mode:** a disposable probe, approved by the lead (*"1, finish the probes"*). Each GPU launch was asked for first (UR-D2). The probe project lived **outside this repo**; its sources are committed beside this doc, in `260929_R_Spike_UnrealRuntime/`, so the probe can be rebuilt.

**The question:** Pass 6's risky part, probes 1–3 of the research doc: can a master wrap Epic's OpenPBR function? Does Unreal render headless and give the same picture every run? Does a packaged app run standalone, and how big is it?

## The short answer

**All three hold.** A script builds an OpenPBR master in seconds, with no GPU. Unreal renders it with no window, and a settled capture is **byte-identical** from run to run. The packaged app runs **with no display at all**, needs about **620 MB**, and runs on any Linux with glibc 2.28 or newer. What is left is ordinary Phase06 work: lighting calibration, anti-aliasing, the rig's scene and camera, and a proper "the material is ready" signal.

## Results

| Probe | Result | Evidence |
|---|---|---|
| 1. Master on Epic's OpenPBR (no GPU) | ✅ | A commandlet (`-nullrhi`, about 6 s) built `M_Matter_Opaque` on `/Engine/Functions/Substrate/MF_Substrate_OpenPBR_Opaque`. 21 parameters registered by their OpenPBR names; it compiled with no errors. |
| 2. Headless render in editor mode | ✅, with one trap | `UnrealEditor <project> -game -RenderOffscreen`: runs 1, 3 and 4 are byte-identical. Run 2 captured Unreal's default checker material (UR-F7). |
| 3. A standalone package | ✅ | `BuildCookRun`: 0 errors, 0 warnings. With `DISPLAY` and `WAYLAND_DISPLAY` unset it runs on SDL's `dummy` video driver. Two runs are byte-identical, and take 26 s then 4 s. |

## Findings

**UR-F4: Unreal 5.8 ships OpenPBR on Substrate, in its core engine.**
- `/Engine/Functions/Substrate/MF_Substrate_OpenPBR_Opaque` and `…_Translucent` are engine content, not a plugin's, so any project packages them.
- **Inputs:** the whole OpenPBR surface under its own names (base, specular, transmission including dispersion, subsurface, coat including `coat_darkening`, fuzz, emission, thin film, geometry), grouped under section-header pins.
- **Outputs:** Opaque gives `OpenPBR_FrontMaterial` and `OpacityMask`; Translucent also gives `Refraction (IOR)`.
- **One naming wrinkle:** Translucent names an input `subsurface_anisotropy`, where Opaque has `subsurface_scatter_anisotropy`.
- **The Interchange plugin's `MX_OpenPBR_*` is a different function.** It takes the same inputs but outputs Unreal's *classic* pins (BaseColor, Metallic, Specular, Roughness, ClearCoat, Sheen…). Wiring it to Substrate's front-material pin fails with *"Material information is invalid"*. Epic's own importer picks the Substrate version when Substrate is on.

**UR-F5: a master can be built by script with no GPU, and needs no binary asset in git.**
- `Scripts/build_master.py` creates the material, calls Epic's function, adds one parameter per exposed OpenPBR input, wires the front material, compiles and saves it.
- It also writes a constant 0.503 Radiance `.hdr` and imports it as the dome's cubemap (`TextureCube`).
- Every Unreal asset the probe used was generated by script. The level is the engine's empty `Entry` map; the app spawns the sphere, lights and camera itself. So **no `.uasset` needs to live in git**; any machine with Unreal 5.8 rebuilds them.

**UR-F6: the first launch compiles shaders for 12 minutes; after that, a run takes seconds.**
- The first editor-mode launch spent about 12 minutes compiling global shaders for this project's settings (Substrate with Adaptive GBuffer, Vulkan SM6).
- It ran with 8 workers (the project's `PercentageUnusedShaderCompilingThreads=75`) at `nice 19`; load average stayed around 6–7 on 32 threads.
- Later editor-mode runs took about 12 s. The package needed no shader compile.

**UR-F7: a capture can catch the default material, so readiness must be checked explicitly.**
- **Run 2** started fast and captured Unreal's default checker material: the master's shaders were not in use yet. `GetNumRemainingJobs() == 0` did not prevent it.
- **The check I tried is not usable:** `FMaterialResource::IsGameThreadShaderMapComplete()` on the master read **0 for 200,000 frames**, even though the master rendered correctly.
- **What the probe settled on:** in editor mode, `FinishCompilation()` on the master's resource at start; then `r.PSOPrecache.ProxyCreationStrategy=0` (the 5.8 name; `…ProxyCreationWhenPSOReady` is deprecated); then 600 settle frames.
- **Phase06 needs a real "the material is ready" signal.** One candidate: check each bound material's render proxy, or render a known reference and verify it before capturing. A cooked package has no on-the-fly shader compile, so this matters most in editor mode.

**UR-F8: the package, measured.**

| Item | Size |
|---|---|
| The whole package (Development) | 1.2 GB |
| Debug symbols (`.debug`, `.sym`) | 270 MB |
| Vulkan debugging layers | about 250 MB |
| An unused AI runtime (the NNE plugin's ONNX Runtime) | 44 MB |
| **What a run needs** | **about 620 MB**: the executable (284 MB) and the cooked content (286 MB) |

- A Shipping build with unused plugins switched off should be smaller. *(Not measured.)*
- The executable's newest glibc symbol is **`GLIBC_2.28`**, so the package runs on roughly every Linux distribution from 2018 on.
- It rendered with no display server, via SDL's `dummy` driver.
- **The Development build writes its own log; Shipping does not.** Use Development for agent runs, or have the app write its own record.

**UR-F9: the package agrees with editor mode, but not to the byte.**
- The two have the same mean (0.21228), and pixels on the sphere differ by 0.9 % on average.
- The editor's render was slightly **warm** (centre 0.416 / 0.416 / 0.407); the package's is **neutral** (0.424 / 0.424 / 0.423). The likely cause is the editor's compressed cubemap (unverified).
- **The package is the reference** for the rig's column. Editor mode is the development loop.

**UR-F10: not calibrated yet (probe 4's job).**
- The centre of the 0.18 grey sphere reads **0.42** linear. A hand estimate for this sun (1.5) and dome (0.503) is about **0.165**, so Unreal is lighting it about 2.5× brighter.
- **Candidates:** the sky light's cubemap scale, a hidden exposure factor in the capture, or light units. Isolate it with a sun-only and a dome-only render.
- **Also not done yet:**
  - anti-aliasing: render large and shrink, like `storm_supersample`;
  - the dome as a visible background (the capture shows black behind the sphere);
  - the rig's camera, sun angle and scene (`JOB_FORMAT.md`).

**UR-F11: what the probe touched outside its own folder.**
- The engine's shared derived-data cache, through its local cache server.
- The build tool's trace file in the per-user Unreal folder (it writes one by default).
- Nothing in the IMRSV project. No Unreal process was running at any launch.
- **Disk:** the probe folder is 4.2 GB, including the package; `/home` has 74 GB free.
- Delete the probe folder when Phase06 is done with it: `~/Documents/Unreal/Probes/MatterProbe` on this machine.

## What this means for "the executable in the repo" (UR-D3)

- **The package goes through Git LFS**, as the textures do: about 620 MB per build if only the files a run needs are committed.
- **The cost is cumulative.** Each master change is a new package, and LFS keeps every version. The repo is public, so every download of the package counts against the organisation's LFS bandwidth.
- **The organisation's LFS quota was not checked** (unverified).
- **For discovery:** commit a stripped Shipping build; rebuild only when a master changes; possibly prune old package versions from LFS.

## Reproduction

The sources are in `260929_R_Spike_UnrealRuntime/`: the project file, config, C++ module, `Scripts/build_master.py` and `Scripts/pfm_to_png.py`. From a copy of that folder (not in the repo; the build writes `Binaries/`, `Intermediate/` and `Saved/` beside it), with `UE` set to an Unreal 5.8 install:

```bash
# 1. the editor target (C++; capped)
nice -n 19 $UE/Engine/Build/BatchFiles/Linux/Build.sh MatterProbeEditor Linux Development \
  -Project=$PWD/MatterProbe.uproject -MaxParallelActions=8 -WaitMutex
# 2. the master and the dome (no GPU)
nice -n 19 $UE/Engine/Binaries/Linux/UnrealEditor-Cmd $PWD/MatterProbe.uproject -run=pythonscript \
  -script=$PWD/Scripts/build_master.py -EnablePlugins=PythonScriptPlugin,EditorScriptingUtilities -unattended -nullrhi
# 3. editor-mode render (GPU; ask the lead first on the UE machine)
nice -n 19 $UE/Engine/Binaries/Linux/UnrealEditor $PWD/MatterProbe.uproject -game -RenderOffscreen -unattended \
  -nosound -MatterOut=$PWD/Saved/MatterProbe/run1.pfm -MatterColor=0.18,0.18,0.18 -MatterRough=0.5
# 4. the package (CPU), then run it with no display (GPU)
nice -n 19 $UE/Engine/Build/BatchFiles/RunUAT.sh BuildCookRun -project=$PWD/MatterProbe.uproject -noP4 \
  -platform=Linux -clientconfig=Development -build -cook -stage -pak -iostore -archive \
  -archivedirectory=$PWD/Packaged -unattended -nocompileeditor -ubtargs="-MaxParallelActions=8"
env -u DISPLAY -u WAYLAND_DISPLAY nice -n 19 Packaged/Linux/MatterProbe.sh -RenderOffscreen -unattended \
  -nosound -MatterOut=$PWD/Saved/MatterProbe/pkg1.pfm -MatterColor=0.18,0.18,0.18 -MatterRough=0.5
# 5. linear PFM -> sRGB PNG (from the Matter Library checkout, for its numpy and Pillow)
uv run python <probe>/Scripts/pfm_to_png.py <in.pfm> <out.png>
```

The app's switches are `-MatterOut=` (a PFM path), `-MatterMaster=` (an object path), `-MatterColor=r,g,b` (sets `base_color`) and `-MatterRough=` (sets `specular_roughness`). A PFM is chosen because it needs no library; the phase may prefer EXR.
