# Runtime Catalog — the prepared JSON catalog consumers read

> **Brought home 2026-09-23** (Phase01 step 1.3) from the IMRSV platform docs. **This repo is now the authority** for this spec; consumers point here.

The **runtime catalog** is the machine-side projection of the authored [manifest](Manifest.md) lockfile: a single JSON file, deterministically generated from the YAML lockfile + the materials tree, that consumers read to list and resolve articles **instead of scanning the filesystem**. The authored YAML lockfile stays the source of truth; the runtime catalog is a derived, committed artifact.

> **Ownership boundary.** **Matter Library** owns curation/release authoring (the `*.lock.yaml`). The **projector** (`tools/converters/project_runtime_catalog.py`) owns validation + projection (YAML → JSON). **Consumers** read a prepared runtime contract (this JSON) — they need a JSON reader only, no YAML parser. The two schemas are separately owned: [Manifest.md](Manifest.md) is the authored source; this doc is the runtime projection.

## Artifact

- **Filename:** `matterlib-<release>.catalog.json` (sits beside the authored `matterlib-<release>.lock.yaml`, e.g. `library/releases/matterlib-0.1.0.catalog.json`). *(Updated 2026-09-23, measured: `library/releases/` holds `matterlib-0.0.1.catalog.json` and `matterlib-0.1.0.catalog.json`, each beside its lockfile.)*
- **Generated by:** `tools/converters/project_runtime_catalog.py` (validates the lockfile, then projects). Deterministic — sorted material order + sorted keys, so a re-run is byte-identical (the catalog-freshness/determinism lane in `tools/validators/run_all.py`).
- **Co-located runtime form:** at runtime the catalog file sits at the root of a directory whose sibling `materials/` subtree holds the payloads; `payload_path` is resolved relative to the catalog file. The versioned install layout is the [install root](../Distribution/ReleaseModel.md).

## Schema

```json
{
  "materials": [
    {
      "creator_selectable": true,
      "display_name": "ABS_Matte_Clean_Base",
      "domain": "synthetic",
      "id": "synthetic/plastic/ABS_Matte_Clean_Base_s01",
      "material_class": "plastic",
      "payload_path": "materials/synthetic/plastic/ABS_Matte_Clean_Base_s01_v01.mtlx",
      "scale": "s01",
      "status": "approved",
      "version": "v01"
    }
  ],
  "release": "0.1.0",
  "schema_version": 2
}
```

*(Updated 2026-09-23, measured: this entry is copied from `library/releases/matterlib-0.1.0.catalog.json`, whose top-level keys are exactly `materials`, `release`, `schema_version` (= 2) and whose entries carry exactly the nine fields in the table below, keys sorted; the former example showed the `0.0.1` pilot with `status: draft`.)*

| Field | Type | Meaning | Source |
|-------|------|---------|--------|
| `schema_version` | int | Runtime-catalog data-contract version (this doc). Bumped on a breaking JSON-shape change — **independent** of the library `release` semver. Bumped `1 → 2` for the additive `creator_selectable` field. Moves `2 → 3` for the `hdris` list and `default_hdri`, **only in a catalog that lists HDRIs**; a catalog without them stays at 2, so every frozen release catalog re-projects byte-identically (§HDRIs, Phase14 Q-P14-2). | this doc |
| `release` | string (semver) | The library release this catalog projects. | lockfile `release` |
| `materials[]` | array | One entry per material, ordered deterministically (by `id`). | lockfile `materials[]` |
| `materials[].id` | string | The qualified Matter identity — Domain/Class folder path + the [qualified name](../Ontology/Identity.md) **including** the `sNN` scale tag. The resolution key (no alias layer). | lockfile `id` |
| `materials[].display_name` | string | Short display label `Material_Variant_Condition_Detail` (the qualified leaf name with the `sNN` tag dropped). UI/display metadata derived from `id`, never a resolution key. | derived from `id` |
| `materials[].domain` | string | The Domain segment of `id` (`natural`, `engineered`, …). | derived from `id` |
| `materials[].material_class` | string | The Class segment of `id` (`stone`, `metal`, `plastic`, …). A consumer's picker filter key is this field ([Glossary](../../Glossary.md) §Material `category`). | derived from `id` |
| `materials[].scale` | string | The `sNN` scale tag off the qualified name (empty for an off-grammar system material with no scale tag). | derived from `id` |
| `materials[].version` | string (`vNN`) | The material's own version axis (never conflated with `release`). | lockfile `version` |
| `materials[].status` | string | Lifecycle status (`draft`/`candidate`/`approved`/`deprecated`/`retired`). | lockfile `status` |
| `materials[].creator_selectable` | bool | Whether the material appears in the Creator-facing browse/assign set. **Default `true`; `false` only on the system material `IMRSV_MissingMaterial`.** Honored by the [Blender Asset-Browser library](../../Glossary.md) generator (`tools/generators/gen_asset_library.py` excludes non-selectable articles from the generated set) and by consumers' browse lists. It is a **browse filter only** — exact system lookup by identity still resolves `IMRSV_MissingMaterial` for the broken-material fallback. | lockfile / derived (default `true`) |
| `materials[].payload_path` | string | Path to the `.mtlx` payload, **relative to the catalog file** (`materials/<id>_<version>.mtlx`; bare `materials/<id>.mtlx` for the off-grammar system material). | derived from `id` + `version` |

*Consumer-side (IMRSV): how the catalog's `material_class` replaced the old shader-family `category` in IMRSV's read surface and picker — see [Consumers](../Consumers.md).*

### HDRIs — a second list beside `materials` *(2026-10-14, Phase14)*

An [HDRI](../../Glossary.md) is a kind beside the taxonomy ([Identity](../Ontology/Identity.md) §HDRI names). A catalog that holds any lists them apart from materials, so a consumer never offers one as the other:

```json
{
  "default_hdri": "IndustrialSunset02_PureSky",
  "hdris": [
    {
      "creator_selectable": true,
      "display_name": "IndustrialSunset02_PureSky",
      "id": "IndustrialSunset02_PureSky",
      "payload_path": "hdris/IndustrialSunset02_PureSky_v01.hdr",
      "status": "candidate",
      "thumbnail_path": "thumbnails/hdris/IndustrialSunset02_PureSky_v01.jpg",
      "version": "v01"
    }
  ],
  "materials": [ … ],
  "release": "0.1.0",
  "schema_version": 3
}
```

*(Measured 2026-10-14: the entry above is the dev catalog's, as `tools/releases/serve_to_stage.py` writes it.)*

| Field | Type | Meaning | Source |
|-------|------|---------|--------|
| `hdris[]` | array | One entry per HDRI, ordered by `id`. **Present only when the release holds HDRIs.** A consumer built before it does not read it (it reads `materials` and `release` by name). | lockfile `hdris[]` |
| `hdris[].id` | string | `<Name>_<Variant>`: the identity, and the resolution key with `version`. | lockfile `id` |
| `hdris[].display_name` | string | The id; UI metadata, never a resolution key. | derived from `id` |
| `hdris[].version` | string (`vNN`) | The HDRI's own version axis. | lockfile `version` |
| `hdris[].status` | string | The lifecycle status, as a material's. | lockfile `status` |
| `hdris[].creator_selectable` | bool | Whether a Creator may pick it. Default `true`. | lockfile / default |
| `hdris[].payload_path` | string | `hdris/<id>_<version>.hdr`, relative to the catalog file. **A scene names the file's bare name** (`@<id>_<version>.hdr@` on a `DomeLight`'s `inputs:texture:file`), found through the stock USD search path on the `hdris/` folder, as a material's `@<Name>.mtlx@` is. | derived from `id` + `version` |
| `hdris[].thumbnail_path` | string | `thumbnails/hdris/<id>_<version>.jpg`: a 1024 × 512 JPEG made from the HDRI (tone-mapped), relative to the catalog file. Made, never stored in git ([`261014_R_MaterialPipeline.md`](../../Planning/Research/261014_R_MaterialPipeline.md) RD-MP-5, RD-MP-6). In the dev install it is made at serve time; in a release it is a release asset *(planned, with the first release that holds HDRIs)*. | derived from `id` + `version` |
| `default_hdri` | string | The id of the HDRI a new scene starts with: **one top-level key, so two defaults cannot be written** (A3). It names a listed HDRI, or the lockfile check refuses the release. | lockfile `default_hdri` |

Provenance, licence and credit stay out of the catalog for HDRIs as for textures (`no_projection_guard`); they live in each HDRI's record, `library/provenance/sources/hdris/<id>.yaml`.

> **Planned (2026-10-14):** a release that holds HDRIs. Staging, freezing and activating one are not built yet, and `tools/releases/freeze_release.py` refuses a lockfile that lists HDRIs until they are (Phase14 §Not now). The dev install serves HDRIs today.

### Planned: the per-article master token *(planned)*

> **Drift (2026-09-23):** the catalog carries **no per-article [master token](../../Glossary.md)** today (measured: no `master` key in either live catalog or lockfile), so consumers still route articles to masters by class rules held in their own code; R14 publishes the master contract as data, which adds the token to the lockfile and this catalog under a future `schema_version` bump — owned by the release-bundle / consumer-contract phase (R14).

> **Update (2026-09-27, Phase07 7.2, ruling L4):** the **dev catalog** that `tools/releases/serve_to_stage.py` projects from the working tree (`matterlib-dev`, the pre-release install that USDLiveView and, through the platform's deploy, Studio read) now carries `materials[].master`, the article's own token read from its `imrsv_metadata.master_material`. Its `status` comes from the recipe (else the release's, else `draft`) rather than always `draft`. The field is additive and `schema_version` is unchanged: measured, Stage lists the catalog and drops the key it does not know. Released catalogs still carry no `master` until R14.

### Groups — Matter, Character and HDRIs *(2026-10-14, Phase15; the dev catalog)*

The library holds three **groups**, each browsed by its own taxonomy ([Taxonomy](../Ontology/Taxonomy.md) §Character; the lead, RD-DS-1). **The dev catalog** (`matterlib-dev`, written by `tools/releases/serve_to_stage.py`) carries them, read from each entry's own file and never worked out from a domain (F-DS-5). **Additive: `schema_version` is unchanged** (2, or 3 with HDRIs). A consumer built before reads `materials` by field name and ignores the rest.

| Field | Type | Meaning | Source |
|-------|------|---------|--------|
| `groups[]` | array | The three groups, in browse order: `id` (`matter`, `character`, `hdris`), `label`, `list` (the list it reads: `materials` or `hdris`), `section` (the value of `group` a `materials` entry carries), `shown` (`rig`, `human` or `thumbnail`: how each is pictured), `taxonomy` (the fields it is browsed by, in order), and for Character `rows` (per species, its parts' `id`s and `label`s, in order: Eyes, Hair, Skin, Nails, Teeth, Mouth). **The same list as the site file's** ([SiteFile](SiteFile.md) §Groups). | `tools/converters/groups.py` |
| `materials[].group` | string | `matter` or `character`. | the `.mtlx`'s `imrsv_metadata` (`group`; absent = `matter`) |
| `materials[].species`, `materials[].part` | string | **Character only:** its species (`humanoid`) and part (`eyes`, `hair`, `skin`, `nails`, `teeth`, `mouth`). | the `.mtlx`'s `imrsv_metadata` |
| `materials[].domain`, `materials[].material_class` | string | On a Character entry, **what it is made of** (`biological` / `tissue`, …): read from the file, since its `id`'s folders are `character/<species>/<part>/`. They no longer say where it is browsed; `group` does. | the `.mtlx`'s `imrsv_metadata` |
| `hdris[].group` | string | `hdris`. | — |
| `hdris[].when`, `hdris[].sky` | string | Its time of day (Poly Haven's category: `sunrise-sunset`, `morning-afternoon`, `midday`, `night`) and its sky (Poly Haven's `weather`: `clear`, `partly_cloudy`, `overcast`, `fog`). **Poly Haven's own words**; grouping them into fewer rows is a consumer's presentation. Left out when the record holds none. | the HDRI's record (into its `.hdr` header at Phase16) |
| `hdris[].tagging` | object | The record's whole `tagging` block (`tags`, `categories`, `attributes`): the platform's ask A10. | the HDRI's record |

- **The 30 Character entries' `id`s changed with their folder** (`character/humanoid/skin/Skin_FitzpatrickIV_Clean_Base_s001`, was `biological/tissue/…`); their names, and so every scene that names one bare, did not ([Identity](../Ontology/Identity.md)).
- **A released catalog carries none of this yet** *(planned, with the first release after Phase15, RD-P15-6)*: the projector is unchanged, so every frozen catalog re-projects byte-identically.
- These are taxonomy fields, not promotion metadata: `no_projection_guard` is untouched. Licence and contributor are Phase16's.

### Off-grammar system material

`IMRSV_MissingMaterial` (`utility/virtual/IMRSV_MissingMaterial`) has no `sNN` scale tag and resolves by bare `<id>.mtlx` (no `_vNN` axis in the filename), carrying a nominal `version: v01`. Its `scale` is empty and its `payload_path` omits the `_<version>` suffix. It is also the sole material carrying `creator_selectable: false` — so it is never offered in the Creator browse/assign set while still resolving by exact identity for the broken-material fallback. See [Manifest.md](Manifest.md) §Off-grammar exception. *(Updated 2026-09-23, measured: in `matterlib-0.1.0.catalog.json` its `scale` is `""`, `payload_path` is `materials/utility/virtual/IMRSV_MissingMaterial.mtlx`, and it is the only `creator_selectable: false` entry.)*

### What the runtime catalog does NOT carry

Per-material **parameter definitions** (`default_parameters`, the LCD parameter set) stay out of the runtime catalog — a consumer parses the resolved `.mtlx` on demand (the runtime catalog maps identity → payload path; the parameter detail comes from parsing that file). This keeps the catalog lean and avoids duplicating `.mtlx` content. *(Revisit only if a parse-free parameter lookup is ever needed — then the catalog grows parameter data; not v1.)* Provenance, licence and evidence never reach the catalog either ([Manifest.md](Manifest.md) §provenance).

> **The website reads a file of its own, not this one** *(ruled 2026-10-14, [`261014_R_TheLibrarysSite.md`](../../Planning/Research/261014_R_TheLibrarysSite.md) RD-WS-4)*. What the library's site needs (the Creator ports, the grounding, provenance, licence, the parity verdict and previews) goes in **a separate file published beside each release**, projected from the same records *(Shipped as a DRAFT, Phase13, 2026-10-14: [SiteFile](SiteFile.md), `matterlib-<release>.site.json`, first published in the dev snapshots `matterlib-0.2.0-dev.N`)*. This catalog stays the engines' lean file, and `no_projection_guard` still holds for it.

## Status

**The runtime contract.** Consumers read this catalog; there is no directory-scan read path. Versioned by its own `schema_version` (currently `2`; `3` in a catalog that lists HDRIs, since 2026-10-14); the catalog seam is additive JSON.

## History

- Pre-standalone (2026-06 → 2026-07): consumers switched from scanning the materials directory to reading this catalog in one hard cutover, with no dual-read period.
- Pre-standalone: the catalog's `category` meaning shifted from shader family to Matter Class once the library went OpenPBR-only, which is why the catalog carries `material_class` and no shader-family field.
- 2026-07-17: `creator_selectable` was added and `schema_version` bumped `1 → 2`.
