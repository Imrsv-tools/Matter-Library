# Site File — what the library's website reads about each article

> **⚠ DRAFT (2026-10-14, Phase13 13.1).** Only the website's staging reads this file, so its shape may still change at little cost, and the change is told to the site's builders in [PlatformDependencies](../../Planning/PlatformDependencies.md) M9. It stops being a draft with the library's first versionable release (research `261014_R_RoadmapOrder.md` F-RO-26). **This repo owns the shape** (RD-WS-4); the site adopts it.

The **site file** is the presentation layer of a release (`261014_R_MaterialPipeline.md` F-MP-13): everything the library's website shows about each article, projected from the article's own records (its recipe, its `.mtlx`, the pilot lockfile's provenance, and the parity rig's scorecard). The [runtime catalog](RuntimeCatalog.md) stays the engines' lean file and is unchanged, and `no_projection_guard` still holds for it. The website is a consumer like any other ([Consumers](../Consumers.md) §The library's website): it reads this file and the release beside it, never this repo.

## Artifact

- **Filename:** `matterlib-<release>.site.json`, published as an asset of the GitHub release (or **dev snapshot**) it describes, beside its pictures, one zip per article and `SHA256SUMS`. A dev snapshot's `<release>` is `X.Y.Z-dev.N` ([NamingConventions](../../NamingConventions.md) §Identifier vocabularies).
- **Generated by:** `tools/releases/build_snapshot.py`, into a git-ignored `library/snapshots/<tag>/`. **Never committed**, and never written to `library/releases/`, whose files the release gates read.
- **Digests:** `SHA256SUMS` (`sha256sum -c` form) covers every asset, this file included. Each picture and zip also carries its own `sha256` here.

## The rule: an absent field means "not known yet"

**A field the library does not hold yet is left out, never filled with a default or a made-up value.** A reader shows the gap honestly: the site draws a labelled swatch where there is no picture, derives nothing it cannot show as derived, and shows no summary where there is none. *(Working Agreement, No Mock Data Masquerading as Real; F-RO-26.)*

## Schema

```json
{
  "schema_version": 2,
  "release": "0.2.0-dev.1",
  "made": "2026-10-14",
  "draft": true,
  "groups": [ { "id": "matter", "label": "Matter", "list": "materials", "section": "matter", "shown": "thumbnail" }, "…" ],
  "materials": [ { "id": "engineered/metal/Copper_Verdigris_Aged_Base_s01", "…": "…" } ],
  "hdris": [ { "id": "IndustrialSunset02", "…": "…" } ],
  "default_hdri": "IndustrialSunset02"
}
```

*(2026-10-16, Phase20 20.2: an HDRI's published id drops* PureSky *([Identity](../Ontology/Identity.md) §HDRI names), from the first snapshot after the switch; `dev.1` to `dev.9` carry `IndustrialSunset02_PureSky`. The site file never lists the old names the dev install keeps for old scenes.)*

| Field | Type | Meaning | Source |
|---|---|---|---|
| `schema_version` | int | This file's contract version, independent of the release and of the runtime catalog's. `1 → 2` (2026-10-14, Phase14 14.3): adds `groups[]`, `hdris[]` and `default_hdri`; nothing in `materials[]` changed. | this doc |
| `release` | string | The release or snapshot this file describes (`matterlib-` is not repeated). | the tag |
| `made` | date | The day it was built. | the builder |
| `draft` | bool | `true` while this spec is a draft. | this doc |
| `groups[]` | array | **What the site shows side by side, in browse order, and how each is shown** (§Groups). | this doc |
| `materials[]` | array | Every article the release lists, sorted by `id`. A dev snapshot lists every article on disk, each with its `status`, the same set as the dev catalog. | — |
| `hdris[]` | array | Every HDRI the library holds, sorted by `id` (§Per HDRI). Absent when it holds none. | — |
| `default_hdri` | string | The id of the HDRI a new scene starts with, as the [runtime catalog](RuntimeCatalog.md) names it. Present with `hdris[]`. | `library/hdris.yaml` |

**Per material — identity** (as the [runtime catalog](RuntimeCatalog.md)):

| Field | Meaning |
|---|---|
| `id`, `version`, `display_name`, `domain`, `material_class`, `scale`, `status`, `creator_selectable` | As the runtime catalog defines them. `creator_selectable: false` only on `IMRSV_MissingMaterial`; a site lists it or not as its browse rule says. |
| `identity` | The qualified name with its version (`Copper_Verdigris_Aged_Base_s01_v01`), the stem every file name below begins with. |
| ~~`label`~~ | **Withdrawn 2026-10-16** (RD-LBL-1, `docs/Planning/Research/261015_R_MaterialLabels.md`): *"the name is the file name … we should not be rearanging filename words to make new names of materials"*. **A reader shows `display_name`**, its underscores as spaces or as breaks between the sections; the words and their order stay the file's. *(Was: the name a person reads, derived from the tokens with the default tokens dropped, or the recipe's `label` where that read badly, Phase13 13.2.)* |
| `master` | The article's master token ([MasterSet](../Ontology/MasterSet.md)). |
| `group`, `species`, `part` *(2026-10-14, Phase15)* | The article's group (`matter` or `character`) and, for Character, its species and part, **read from the article's own file** ([RuntimeCatalog](RuntimeCatalog.md) §Groups). `domain` and `material_class` are read from the file too: on a Character article they say what it is made of, not where it is browsed. |
| `section` | Where it is browsed: `matter`, or `character` beside it. **Since Phase15, the file's `group`** (until then worked out from the domain, `biological` → `character`, which RD-DS-1 ruled wrong for a generic biological material). **Biological materials (skin, eyes, teeth, hair, nails) are not Matter**: they stay browsable, apart, and are shown in a human context (skin on a side face and hands, an eye on an eye), **never on the rig's cubes**, so a `character` material publishes no rig picture until such a picture exists (the lead, 2026-10-14, Phase13 RD-P13-2; its subjects are *Thumbnails*' RD-MP-3). Its verdicts, still evidence, stay under `parity`. *(Other kinds, such as HDRIs, are not sections: each is a list of its own beside `materials`, as in the [runtime catalog](RuntimeCatalog.md), added by its own phase: HDRIs by Phase14, §Per HDRI.)* |
| `meters_per_tile` | The real-world size of one texture tile, from the article's metadata. |

**Per material — what a Creator may change:**

| Field | Meaning |
|---|---|
| `controls[]` | Each Creator port the article declares ([LCDSchema](LCDSchema.md)): `port`, `name` (its UI name), `type`, `start` (the article's own value: a number, or a list per channel) and `range` (`min`, `max`, `null` where open; `min_exclusive: true` where the minimum is not allowed, `uv_scale`). Ranges are LCDSchema's frozen ones, per channel. |
| `wear_layers[]` | Each wear layer: `layer` (its name, e.g. `Dust01`), the `density_port` that turns it up and, for a deposit, its `color_port`. Absent on an article with none. |

**Per material — where it came from** (the compliance layer, as far as the library holds it):

| Field | Meaning |
|---|---|
| `licence` | `CC0-1.0`, every article (RD-RO-2). Read from the article's own `.mtlx` since Phase16 (2026-10-14). |
| `sources[]` | The recipe's sources: `kind` (`ambientcg`, `physicallybased`, `procedural`, `judgement`) with what that kind records (an `asset` and `url`, the values used, a `why`). For a pilot article whose recipe has none, its textures' lockfile provenance (`kind`, `license`, `url`), wear layers excepted: like a recipe's, these sources are the article's own, and its wear layers are under `wear_layers`. Absent when nothing is recorded. |
| `contributor` | A contributor's handle, when one was given: credit as a courtesy and for the platform's Forseti tracking, never a licence condition (RD-RO-2). **Since Phase16 (2026-10-14, `matterlib-0.2.0-dev.5`)** read from the article's own `.mtlx` (its `imrsv_metadata`); the library's own articles say `MatterBot` (RD-P16-11). Left out when the file declares none. |
| `fits` | *(2026-10-15, Phase18, `matterlib-0.2.0-dev.8`)* The part mesh a fitted Character material's own picture is painted for (`MakeHuman_Teeth_v01`, …), read from its `.mtlx`; its kit is the `kits[]` entry with that `id` (§Kits). Left out on every other material. |
| `origin` | Where the article came from, any of: `scan` (a scanned source, e.g. ambientCG), `procedural` (a generator), `measured` (measured values, e.g. Physically Based), `agent-drafted` (an agent wrote the recipe). Derived from its sources at 13.2, kept in the recipe, confirmed by the maintainer (F-MP-18). Absent until written. |

**Per material — evidence and pictures:**

| Field | Meaning |
|---|---|
| `parity` | Present when the parity rig has rendered the article. `tools` (which of `storm`, `blender`, `unreal` ran), `scene` (the rig's test scene), `measured` (the date of the rig's scorecard, absent if it has none) and `controls` (per port: `verdict`, the worst of its rows, and `rows[]` each with its `setting` and `verdict`). The words are the rig's own Moved verdicts: `moved alike` · `UNEVEN` · `ONE-SIDED` · `no change in any tool` ([_Architecture](../_Architecture.md) §LCD). **A control with no entry was not swept**, which is not a pass. **Evidence is published as measured:** a picture or verdict older than the current masters or Unreal runtime says so only through its date (Phase13 Q-P13-4). |
| `pictures[]` | `role`: `thumbnail` or `rig`, thumbnails first. **`thumbnail`** *(since Phase17 17.5, first in `matterlib-0.2.0-dev.6`)*: the material shown at its best on a subject that suits it ([Catalog](../Catalog/Catalog.md) §Thumbnails), with its `view` (Matter: `card`, `close`, and `dark` for an emitter; Character: `face`, `hand`, `mouth`, `lips`, `eye` or `head`, never the whole body, the waist or the feet), the `renderer` named (`Cycles (Blender 5.2.2 LTS)`), `file` (`<identity>__thumbnail__<view>.jpg`) and `sha256`; JPEG at 1024 px. A material whose thumbnails are not made yet has none (a draft gets its own when it comes to review); a thumbnail older than its article or the masters is refused by the builder, never shipped. **`rig`**, the evidence: `tool`, `view` (`wide` or `close`), `file` and `sha256`. **Only the test scene's default pictures** are published: never a character render, a sweep picture, or a rig log or job file. JPEG, at the rig's 512 px. **Every picture the file names is a baseline JPEG** *(since `matterlib-0.2.0-dev.7`; WebP until then)*: the website, Blender and Unreal all read it, and Unreal reads no WebP (the lead, 2026-10-14; the platform's PIC-F3). |
| `download` | `file` (`<identity>.zip`), `bytes`, `sha256` and `textures` (how many). The zip holds `<identity>.mtlx` with every texture reference rewritten to `textures/<name>`, and those textures, shared wear layers included, so it opens anywhere with no search path. **Fit-set pictures** (hair cards, eyes) are supplied when an article is bound to a mesh, never referenced by it, so they are not in the zip. |
| `summary`, `search_words` | A one-line public description and the words a search should find it by, written by the agent and confirmed by the maintainer with the picture (F-MP-14). |

## Groups — what sits beside what *(2026-10-14, Phase14 14.3)*

**The library relays, as data, which groups the site shows side by side, so the site builds its browsing from the library and not from its own assumptions** (the lead, 2026-10-14, RD-P14-4: *"make sure the other things sitting next to it are relayed as well (We ruled the character materials need to not be at taht level as they need a different view apprach instead of cubes"*). In browse order:

| `id` | `label` | `list` | `section` | `shown` |
|---|---|---|---|---|
| `matter` | Matter | `materials` | `matter` | `thumbnail`: by its own thumbnails, each on a subject that suits it *(since Phase17 17.5, RD-P17-4; until then `rig`, the parity rig's test scene, whose pictures stay as evidence)*. **Only in the site file:** the dev catalog keeps `rig`, because the dev install serves no thumbnails yet. |
| `character` | Character | `materials` | `character` | `human`: in a human context (skin on a side face and hands, an eye on an eye), **never on the cubes** (RD-P13-2). Its pictures are its thumbnails, on the clothed character *(since Phase17 17.5)*; until then none was published. |
| `hdris` | HDRIs | `hdris` | — | `thumbnail`: the HDRI's own 2:1 picture |

**Since Phase15 (2026-10-14), each group also names its `taxonomy`**, the fields it is browsed by, in order (Matter `domain`, `material_class` · Character `species`, `part` · HDRIs `when`, `sky`), **and Character carries its `rows`**: per species, its parts' `id`s and `label`s in order (`humanoid`: Eyes, Hair, Skin, Nails, Teeth, Mouth; the website's ask M11 (1)). Additive: `schema_version` stays 2. The dev catalog carries the same list.

A group reads the list it names, filtered by `section` where it gives one. **A group is a place to browse, not a [Domain](../Ontology/Taxonomy.md):** Matter and Character are sections of `materials`; an HDRI is a kind beside the taxonomy ([Identity](../Ontology/Identity.md) §HDRI names).

## Per HDRI *(2026-10-14, Phase14 14.3)*

**Thumbnails and credit only** (RD-P14-4): an HDRI's `.hdr` file is not published in a snapshot, so an entry has **no `download`**. Every credit field is Poly Haven's own, as the HDRI's record holds it (`library/provenance/sources/hdris/<id>.yaml`); a field the record does not hold is left out.

| Field | Meaning |
|---|---|
| `id`, `version`, `display_name`, `status`, `creator_selectable` | As the [runtime catalog](RuntimeCatalog.md) §HDRIs defines them. |
| `identity` | `<id>_<version>`: the file's stem, which every asset name below begins with. |
| ~~`label`~~ | **Withdrawn 2026-10-16** (RD-LBL-1): an HDRI's name is its file name; a reader shows `display_name`. The source's own title moves into `credit.title`. *(Was: the source's own name, `Industrial Sunset 02 (Pure Sky)`, or one derived from the tokens.)* |
| `description` | The source's one-line description, **without its opening resolution claim** (*"Free 16K HDRI, unclipped: …"*, which read as a claim about the library's 4096 × 2048 file; Phase16, RD-P16-4, the website's ask M11 (3)). The source's own words stay in the record. |
| `licence`, `contributor` | `CC0-1.0`, from the record; and who brought it into the library, `MatterBot` for the library's own (Phase16, RD-P16-11). Poly Haven's people are in `credit`. The same facts are in the served `.hdr`'s header ([Identity](../Ontology/Identity.md) §HDRI names). |
| `credit` | `title` (the source's own title for it, `Industrial Sunset 02 (Pure Sky)`: credit, never its name, RD-LBL-1, 2026-10-16), `source` (`Poly Haven`), `source_url`, `asset_url` (its page there), `authors[]` (each `name` and `role`, e.g. *Original*, *Sky Edits*), `sponsors[]` (each `id`, `name` and `url` where given) and `edited_from` (the source's line naming the HDRI a sky was edited from, as Markdown), with **`edited_from_name` and `edited_from_url`** beside it, the same as a name and an address *(Phase16, RD-P16-3, the website's ask M11 (4); the Markdown line stays until the site has moved)*. |
| `group`, `when`, `sky` *(2026-10-14, Phase15)* | `hdris`, and the HDRI's two browse axes, in Poly Haven's own words: `when` its time category (`sunrise-sunset`, `morning-afternoon`, `midday`, `night`), `sky` its `weather` (`clear`, `partly_cloudy`, `overcast`, `fog`). Read from `tagging`; left out when it holds none. |
| `tagging` | The source's own `tags`, `categories` and `attributes` (`time_of_day`, `weather`, `light_type`, `contrast`, `environment`, `sky_view`, …): **what a search and a filter on the site read.** |
| `captured` | `date_taken`, `whitebalance`, `evs_cap`, `coords`, where the source gives them. |
| `pictures[]` | One entry: `role: thumbnail`, `file` (`<identity>__thumbnail.jpg`, 1024 × 512, tone-mapped from the HDRI by `tools/releases/hdris.py`) and `sha256`. |

## Kits *(2026-10-15, Phase18)*

`kits[]` (top level, absent when there is none): **what a contributor paints a Character material against**, one entry per part mesh, in `tools/converters/groups.py`'s order. `id` (`MakeHuman_Teeth_v01`), `family`, `species`, `what` (a sentence), `parts` (the Character parts it serves), `rig_parts` (the pieces the rig and Studio split it into), `map_size` (the picture's side, px), `uv_sha256` (the layout's hash: what makes it this version), `file` (`kit__<id>.zip`, a release asset) and its `sha256`. The zip holds the mesh with its UVs (USD and OBJ, metres, Y up), its layout picture, its islands picture and a README. CONTRIBUTING.md §3.1 is the path.

## Limits

GitHub allows up to 1000 assets a release, each under 2 GiB. A dev snapshot publishes at most nine per article (six rig pictures, two thumbnails and a zip; *until Phase17, seven*), one per HDRI (its thumbnail) and one per kit: with 59 HDRIs that fits about 100 articles at worst, and `matterlib-0.2.0-dev.8` is 580 assets for 97 and four kits. The builder fails rather than drop an asset past the limit. Splitting belongs to the release-bundle phase (F-MP-30).
