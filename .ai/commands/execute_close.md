# `/execute` — stage 5, the Close

> **Sibling of [`execute.md`](execute.md). Read this ONLY when you are running the close** — the run that
> actually finishes the phase. Most `/execute` runs suspend (`execute.md` §STRENGTHEN) and never come here (one phase took **8** runs;
> exactly **one** reached the close). Split out for that reason: the close is a distinct job with its own discipline,
> so every run paid a second Read for a section 7-in-8 of them never used.

**⛔ A CLOSE MAY LAND APPLICATION CODE, AND THAT IS NOT A CONTRADICTION OF "CEREMONY OVER FINISHED WORK".** Row `A0`'s preferred path is **FIX**, so a close can legitimately ship a new file, a new hook and a set of new assertions — **the close is where the acceptance sentence is finally read against reality, and reality is allowed to lose.** Such a run *feels* wrong from inside (one lead called it *"the strangest close ever"*) and the strangeness is **structural, not a mistake**: the alternative is a phase that closes green over a defect its own headline invariant forbids. **Hold the same bar as any other landed work** — a gate that can fail, a RED demo, an Execution-Log entry — and say plainly in the handback that the close carried code.

**Prerequisite:** you arrived here from `execute.md` §Handback. The close is **lead-initiated** —
never self-initiate it. **Issue mode does NOT use this close** — run the light close per `execute.md`'s Issue-mode note.

**The close — run it in this order.** (The prose below the table is the backing detail for each row; read the row, drop into the prose only for the one you're on.)

| | Step | The catch that gets missed |
|---|---|---|
| **A⁻** | **⛔ PRE-CLOSE FETCH + DIVERGENCE CHECK — run this FIRST, before A0.** | **`git fetch origin main`, then `git rev-list --count HEAD..origin/main`.** If you are behind, a parallel workstream landed on the trunk during the close (a same-day sibling push is not exotic here) — **SURFACE the divergence and converge / hand off BEFORE building the close commit**, so it sits on the trunk you'll actually push to, not a stale anchor. |
| **A0** | **⛔⛔ ACCEPTANCE-INVARIANT BLOCK — mechanical, NOT self-scored. Run this BEFORE row A.** | **⛔ ARMING GATE, ONE QUESTION, ANSWER IT BEFORE READING THE REST OF THIS CELL: does the Goal/Acceptance contain an ABSOLUTE QUANTIFIER — *"no deferrals"* · *"no placeholders / stubs"* · *"every X"* · *"all Y"* · *"fully functioning"*? **NO → this row does not arm. Skip to row A.** YES → read on.** *(This gate is new because the cell is ~900 words that resolve to "not armed" for most Goals, and you had to read all of them to learn it. It does not weaken the row: the row's own war story is about an agent that **rationalised**, not one that failed to read.)* **⛔ THEN, AND THIS IS THE PREFERRED PATH — ASK WHICH DEFER ITEMS YOU CAN SIMPLY *FIX*. A fixed item LEAVES the list, and an empty list does not arm this block at all.** Only what genuinely remains gets routed to the lead, verbatim, with the acceptance sentence adjacent. **Then, for whatever remains: if the phase Goal/Acceptance contains an ABSOLUTE QUANTIFIER — "no deferrals" · "no placeholders / stubs" · "every X" · "all Y" · "fully functioning" — a NON-EMPTY DEFER list is an AUTOMATIC BLOCK.** You may **not** close it on your own judgment. **Route it to the lead**, verbatim: *"the Goal says `<quote the acceptance sentence>`; I am holding `<N>` DEFERs `<list>`. Override, or re-open?"* **And paste the Goal's acceptance sentence textually ADJACENT to the DEFER list** in the close message — the contradiction must be side-by-side, not 1,500 lines apart. **Why this is mechanical and not interpretive:** the agent that wants to close is the agent scoring the gate, and it rationalizes. One phase's Goal said *"No placeholders, no stubs, no deferrals"*; the executor ran row A, walked a **6-item** DEFER list, judged each "orthogonal," shipped a `🎉` — and the lead's verdict was that the phase **had not met its goal**. It even carried the SQ1 precedent (a 🎉 claiming "a dropped field is impossible to ship" while holding a 6-item DEFER list *of dropped fields*) and **did not recognise itself in it.** The correct answer was available from the Goal text alone, with zero investigation. *(Deferral test itself: `feedback_corrections_dont_defer`.)* **⛔ TWO THINGS THIS BLOCK MUST NOT BE READ WITHOUT.** **(1) DISCHARGING IT BY *FIXING* — an item you fix leaves the list, and an empty list does not arm the block.** Row A already says deferral is the WORST case, not the default; **a one-line correction you are able to fix is not a deferral you must escalate.** Stated only as "block or route", this row reads as offering exactly the two failure modes — an agent reading it literally BLOCKS a closeable phase over a stale sentence in a doc, and an agent reading it loosely rationalizes the list as "orthogonal" and ships. **The safe third path is FIX, and it is the preferred one.** **(2) WHAT COUNTS AS AN OPEN DEFER: an item still UNDISPOSITIONED at close time.** An item **the LEAD already ruled out of scope at plan time** — a phase-doc keep-list / allowlist of *"residue this phase deliberately does not touch"* — is **DISPOSITIONED, NOT DEFERRED.** Record each in the ledger as `ruled out (plan keep-list)`; it does **not** arm this block. Treating a lead-pre-ruled keep-list as open DEFERs would block closes on work the lead had already decided against, which inverts the row's purpose. **⛔ (3) A FOURTH DISPOSITION — `ALREADY ROUTED` — FOR THE ITEM THE LEAD HAS SEEN AND CLOSED OVER.** FIX / BLOCK / ROUTE do not cover the commonest attended case: **you already routed it, in the handback the lead was replying to, and they said close.** Blocking again re-litigates a decision the lead just made with the item in front of them. **The test, and it keeps this mechanical:** the deferral was stated to the lead **verbatim and adjacent to the completion claim**, in the message they answered with a close instruction. **The guard that makes a wrong reading visible: quote BOTH the deferral and the lead's exact reply in the `🎉` commit**, so anyone can overturn it by reading one commit message. *(Without this path the honest agent blocks a phase the lead has closed, and the loose agent stops recording why it didn't. One run had to invent this reasoning at the close — on the row whose entire purpose is to be mechanical rather than interpretive.)* **⛔ AND `ALREADY ROUTED` RESOLVES THE *BLOCK*, NEVER THE *HEADLINE*.** Row A says *"if you will not fix a correction you must DEMOTE THE `🎉` HEADLINE to what actually shipped"*, and read beside this path the two look like they point opposite ways on one item. **They govern different objects: the lead's close instruction settles WHETHER YOU MAY CLOSE and settles nothing about WHAT THE `🎉` MAY CLAIM.** So close — and still write the headline to what shipped. An absolute quantifier the shipped work does not satisfy is wrong however the item was dispositioned. *(A close routed a sitemap exclusion `ALREADY ROUTED`, correctly, and then could not tell whether row A obliged it to demote a headline the lead had just approved. Row A does not govern the disposition; it governs the wording.)* |
| **A** | **Doc-conform close-gate** (BLOCKING, before anything else) | Re-read the Goal/Acceptance **verbatim** and assert it holds against committed reality **including the open DEFER list** — step-completion ≠ goal-achievement. **⚠ AND CONFORM THE GATES' OWN OUTPUT STRINGS, NOT ONLY THE DOCS.** A summary line describing the old shape is **read straight out of the CI log by everyone who never opens the doc**, and nothing else sweeps it. **⚠ AND ASK: IS ANYTHING IN THIS PHASE STILL AWAITING A LEAD RULING?** An unratified placeholder is sanctioned mid-execute (`execute.md` §Divergence), but nothing previously asked before stamping `🎉` — **name every such item as a numbered `⛔ YOUR CALL` entry with its reversal cost and your recommendation.** Recording it is enough; it does not block the close. Then make every durable spec match shipped code, **platform-level docs included**. **⛔ AND IF THE CLOSE LANDED APPLICATION CODE (row `A0`'s FIX path, which is the preferred one), RE-RUN THE PHASE'S OWN NON-MUTATING GATES OVER THE CHANGED SURFACE — not only the always-on three.** A close-time fix is code that no gate has seen, arriving at the moment ceremony is heaviest and attention lowest. ⚠ **Skip only the gates that MUTATE** (`execute.md` warns against invoking those for information) — **name each one you skipped and why**, because otherwise CI's run on the push is the first time they have ever met this phase's code, and row D has just stamped it. *(One close ran typecheck/lint/format and one gate it happened to check for an unrelated reason, and left four reader gates unrun over a hook it had just written.)* |
| **B** | **Doc moves + phase-doc self-finalize** | Phase doc → `Planning/Phases/Complete/` (+ the Wave sequencer if this is a Wave's last open member — **⛔ that update is MECHANICAL ONLY; row B⁺ governs whether the Wave may be called closed, and it is not this row's call**); `Roadmap.md` entry → bottom of `## Complete` (**entry = `Outcome` + status + pointer ONLY — the long legacy entries are NOT the template**, `feedback_build_plan_entry_scannable`). **⛔ AND "ONLY" HAS A MECHANICAL CEILING, BECAUSE THE WORD ALONE DEMONSTRABLY DOES NOT HOLD: heading · one `Outcome` line · one pointer line · AT MOST ONE italic line of context. FOUR LINES. Count them before you commit.** *(Two consecutive closes wrote **eight and ten paragraphs** — findings, `⭐`/`⛔`/`⚠` rulings, deferral ledgers, unpushed-gate warnings — into entries governed by this rule, with this rule in context. The lead's ruling: **"they are starting to use the roadmap as some sort of project tracker … NO … details only in the phase docs."**)* **⛔ EVERY ONE OF THOSE PARAGRAPHS WAS ALREADY A NUMBERED ITEM IN THE PHASE DOC THE ENTRY POINTS AT** — so the Roadmap copy adds nothing and goes stale on its own schedule. **The pull is real and worth naming: at the close you have just finished the phase's best analysis, and the Roadmap is the doc you know the lead opens — so putting it there feels like making sure it is SEEN. It is making sure it is DUPLICATED.** A finding that must reach the lead **now** goes in the **handback**, which they read once; the index is re-read forever. **The Roadmap is an INDEX, not a tracker and not a findings surface.** **FINALIZE THE PHASE DOC ITSELF** — flip its `**Status:**` → `🎉 COMPLETE (closed <date>)`, append a `CLOSE — DONE` Execution-Log entry, mark the live Resume block historical; **grep the moved doc for `IN EXECUTION` / `READY FOR CLOSE` before the `🎉` commit** — a moved-but-unfinalized doc still reading as open is the default failure mode (the lead had to manually ask "verify the doc reflects the close"). **And verify the finalize IN HEAD, not only the working file:** after the docs close commit, `git grep "COMPLETE (closed" HEAD -- <moved path>` + assert `git status --short` clean — a `git mv` rename commit can stage a **pre-finalize (stale) blob** while the working tree stays correct (observed once: `rename (100%)` committed without the finalize edits; recover via explicit-path re-commit + HEAD re-verify). **⛔ THE MOVE PUTS THE DOC ONE LEVEL DEEPER — RE-BASE EVERY RELATIVE LINK, AND RESOLVE EACH AGAINST THE TREE AFTERWARDS, NEVER BY EYE.** `Phases/X.md` → `Phases/Complete/X.md` silently changes what every `../` in the file means: `../Research/…` now resolves to `Phases/Research/`, **which does not exist**. `grep -o ']([^)]*)' <doc>` and existence-test each target. **Watch the INVERSE case too — a link written as `Complete/Phase02_…md` was CORRECT before the move and is wrong after**, because the doc is now *inside* `Complete/`. **Nothing goes red for this**: markdown links fail no build, no gate resolves them, and the doc looks right in the editor where it was authored — which is why it is invisible at exactly the moment this table calls maximum pressure. **⛔ AND THAT IS ONLY HALF THE MOVE — GREP THE TREE FOR THE OLD PATH BEFORE YOU FINISH.** Outbound links are the half you can see from inside the doc; **inbound links are the half the move actually breaks**, and `Phases/<Name>.md` is linked FROM `Roadmap.md` and often from sibling phase docs. **⛔ AND ANCHOR THE `## Complete` ENTRY ON THE SECTION HEADING, NEVER ON A SIBLING PHASE'S ENTRY — then `grep '^#\+ Phase<NN>'` and assert exactly ONE match.** A Wave's member listing inside `## Active` repeats phase headings that also appear in `## Complete`, so **a phase-name anchor is ambiguous by construction**. |
| **B⁺** | **⛔ CLOSING A WAVE IS NOT THE ARITHMETIC OF ITS MEMBERS** (only when this phase is a Wave's last open member) | **⏭ NOT A WAVE MEMBER — OR NOT ITS LAST OPEN ONE? SKIP THIS ROW ENTIRELY, IN ONE LINE.** (Added because this row was read in full, ~250 words, only to conclude N/A — the conditional in its own heading is not enough on its own.) **Row B's Wave clause is a MOVE/UPDATE chore. This row is a JUDGMENT GATE and it is not discharged by it.** Before writing anything about the Wave: **open the Wave doc, read its `## Exit gate` VERBATIM, and assert EACH CLAUSE against committed reality.** A Wave gate is typically a **conjunction *beyond* member completion**, and **the clause most likely to be unmet is one an earlier member closed with a STATED GAP** — a cut prototype, a deferred guard, an open issue. **You MAY update the Wave sequencer's member list. You may NOT stamp the Wave closed** — that is a lead ruling. Record the honest state: *"all N members closed, `<k>` exit clause(s) unmet — `<clause>`, tracked at `#<n>`"*. **This is the `A0` failure mode one level up:** `A0` protects a *phase* `Goal` from being self-scored off its step ✅s; nothing protects a *Wave* gate from being self-scored off its member ✅s — **and this inference is more seductive, because "all six are closed" feels like arithmetic rather than judgment.** |
| **C** | **Issue-close coda** (issue-sourced phases; BEFORE the commit) | Per issue: comment the resolution (cite the doc/work, **not** a SHA — it doesn't exist yet) → **drop the `status:` label** → `gh issue close`. Pre-authorized; don't stop to ask. |
| **D** | **The `🎉` commit** | The `🎉 PHASE COMPLETE` commit with **`Refs: #n`** (never `Closes:`). **⛔ FIRST ASK WHETHER YOUR COMMITS ARE ALREADY ON THE REMOTE — "I have not pushed" IS NOT "CI has not run".** On a repo whose defining property is concurrent sessions on one branch, **a sibling's push carries your commits**, so both the provisional clause and the unpushed-range line below can be false the moment you write them. `git merge-base --is-ancestor <your-sha> origin/main`, then read the run. *(One close wrote "the whole phase executed unpushed, eleven commits" into its own `🎉` body; row E's pre-push count came back **1**, not 12 — a sibling had already carried the other eleven and CI had run them green. Two statements in a close commit, false within minutes, and it had to be amended.)* **⛔ IF THIS PHASE'S GATES GENUINELY HAVE NEVER RUN IN CI, THE `🎉` IS *PROVISIONAL* UNTIL A RUN IS OBSERVED — say so in the commit body and in the handback, and do not treat the close as finished until you have READ the run.** Row D precedes row E, so the stamp is applied and the acceptance gate scored **before the only environment that can contradict them executes**. **And if the phase has been unpushed for its whole execution, say so in one line with the commit range** — nine steps each honestly recording `CI ✗ NOT RUN` is nine correct entries whose **accumulation is invisible**, precisely because every instance was individually true. *(One close followed this order exactly and within four minutes of pushing CI falsified **two** of the close commit's own statements: a real defect the phase introduced — a gate's PREPARE needed a network nothing had created, green on every machine that had ever run the stack, dead at 27s on a cold runner — and a misattributed red. ⇒ **Looking was cheap and immediately productive: one push, ~11 minutes of CI, one real defect and one bad classification. The cost of the debt was far lower than the cost of carrying it, and the close is the moment to pay it.**)* **⛔ AND NAME THE ACT THAT DISCHARGES THE PROVISIONAL STAMP, BECAUSE THE PHASE DOC IS ALREADY MOVED, FINALIZED AND COMMITTED BY THE TIME THE RUN FINISHES.** When it completes, append one line to the closed phase doc's `Status:` — **`✅ CI OBSERVED <date> — <run URL>, <n> green / <n> red, and whether any red is this phase's`** — in **its own commit**. *That* commit finishes the close. *(The pattern existed as unwritten precedent in three closed phase docs before it was a step, and each run had to rediscover it by grepping a sibling.)* |
| **E** | **PUSH — the ONE human gate.** | **Stop and ask before pushing.** |

**The close in detail — per-row backing (drop into the row you're on):**

**A⁻ / A0** — fully specified in their table rows above (pre-close fetch+divergence · the acceptance-invariant block).

**A — the BLOCKING doc-conform close-gate (before the `🎉` commit) — the step that always gets skipped, so do NOT:**
- FIRST re-read the phase Goal/Acceptance **verbatim** and assert it holds against committed reality *including the open DEFER list* — step-completion ≠ goal-achievement when the goal is an invariant.
- **Build the DEFERRAL LEDGER (Workflow §Phase Workflow, stage 5 — loose-end disposition):** table every open thread and disposition each — `fixed` · `ruled out (+ the spec line)` · `deferred as an ADDITION (+ why it is not a correction)`. **The test is "ADDITION or CORRECTION?" — NEVER "is it big?"**. A **CORRECTION to a surface THIS phase authored** — an exposed-but-unconsumed param · a field nothing applies · faked/approximated behavior · **a missing example the current spec already promises** — is **IN-SCOPE: fix it / route to the repair loop (`execute_repair.md`). It is never deferrable.** Only a genuinely orthogonal **addition** may defer (new scope · a *pre-existing* defect you merely discovered · a product/contract call that is the lead's). **If you will not fix a correction, you must DEMOTE THE 🎉 HEADLINE to what actually shipped** — you may not ship `✅ COMPLETE` *and* a list of gaps in the thing you just completed. **Deferral is the WORST case, not the default** (two-thirds of every issue ever filed is a phase punting its own work — the lead has called this out hard).
- **Grep your own 🎉-body completion claim** ("impossible to ship / complete / green / done") against the DEFER list before committing.
- THEN review + update the durable docs against the WHOLE phase, now tested-and-clear. **Doc-conform = refine + annotate, never delete forward-looking content:** correct stale facts and add "Shipped (Phase NN)" notes, but PRESERVE aspirational/future-scope descriptions (mark them not-yet-shipped) — a delegated doc-conform brief MUST carry that constraint. Conform the surfaces where a root-cause/finding was established even when its fix deferred to an issue (the phase's commit messages carry them). **⚠ A delta the plan sequenced as its own `[spec-edit]` STEP is already landed — VERIFY it here, do not re-author it** (`execute.md` §STRENGTHEN owns that precedence). **And before conforming any durable doc, grep the open tracker for issues naming that same doc and fold their checklists in** — a phase's own discovery files issues against the docs it will later conform, and the two lists name different defects.
- For every surface the phase changed make the durable spec match shipped code, plus any `Learnings/` entry earned. **Work from the phase's commits (`git log` over the phase range) as the to-do list**; grep the changed symbols/ops/versions, refresh each stale spot, and cross-check each plan step's named deliverables against committed reality (a headline-shipped-but-sub-deliverable-missing step surfaces here).
- **A LARGE doc-conform sweep may parallelize: Bash-less subagents DRAFT the per-doc conform edits; YOU `Read` each target and land the edits yourself** — a subagent's Read never satisfies your session's Read-before-Edit gate, and the refine-don't-delete judgment stays with you.

**B — doc moves + phase-doc self-finalize:** move the phase doc to durable `Planning/Phases/Complete/` (+ the Wave sequencer if this phase is a Wave's last open member — **row B⁺ first: read the Wave's `## Exit gate` before writing any Wave status anywhere, including `Roadmap.md`**); update `Planning/Roadmap.md`. Then the finalize + IN-HEAD verify exactly as row B states.

**C — the issue-close coda** (issue-sourced phases; BEFORE the commit): per source issue — comment the resolution citing the phase doc / the work (*not* a commit SHA, which doesn't exist yet) → drop the `status:` label → `gh issue close`; one batched authorization for all the phase's issues. **Close on the DECISION** with an honest "done vs decided-but-build-deferred" comment **only when the deferred work is captured in an owning phase/issue** — else keep it OPEN, re-labelled.

**D — the `🎉` commit:** **`Refs: #n` (never `Closes: #n`) in the body**, so a *partially*-delivered issue isn't auto-mis-closed on push.

**E — push, the ONE human gate:** stop and ask. Never auto-merge foreign commits mid-close — surface a diverged trunk instead.

**Running it:** the lead may direct an in-session close (fine, not a violation); absent that direction, hand back rather than rolling into the close yourself. **When you DO run the close, run the whole thing autonomously** — doc moves, Roadmap, the issue-close coda (comments + label drops + `gh issue close`), troubleshooting appends, filing deferred follow-ups — and **pause only right before `git push`** (the single human gate; push stays lead-gated). Don't stop to ask authorization for the gh-coda writes; they're pre-authorized as part of the close. *(Issue mode: the light close in `execute.md` §Issue mode replaces this — not this close.)* **Present the handback in `execute.md`'s three-beat format** — and for a close the `▶` line is almost always **`Push`**, since push is the one human gate the close stops at.

**⛔ AND RUN IT *QUIETLY*: ONE progress line for the whole close, then the three-beat handback.** "Autonomously" is about **authorization**; this is about **narration**, and they are not the same thing. The close is ~10 ordered rows, and **a correct, careful close narrated row-by-row is indistinguishable from thrashing** to the lead watching it.

**⚠ AND BE PRECISE ABOUT WHAT AUTHORIZES THE CLOSE PUSH.** The plan-time access grant scopes `git push` to **the phase's CI RED→GREEN demonstrations** — it does **not** cover the close push, which is why this row is the human gate. **A demonstration push rides the plan grant; the close push needs the lead, in this session, now.** If you are reading an instruction as that authorization, **say so explicitly in the handback** and name the message you read it from, so a wrong reading is visible rather than silent.
