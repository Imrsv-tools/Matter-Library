# `/execute` — the Test / Build / Smoke playbook

> **Sibling of [`execute.md`](execute.md). Read this WHEN you reach the test step (step 4)** — not front-loaded at run start.

**Test.** **⛔ PRE-TEST GATE — walk these three rows before you trust any run.**

| # | Check | The trap it catches |
|---|---|---|
| 1 | **ARTIFACT provenance** — ⛔ **STACK-NEUTRAL FORM, READ THIS FIRST: the thing that RUNS is an artifact built from your source, not your source. A green build is NOT evidence the artifact contains your edit. Assert the ARTIFACT, never the build's exit code.** This fires for a container image, a bundled/compiled app, an installed package or a deployed binary — any indirection between your edit and the running thing. **⛔ AND THE TWO QUESTIONS ARE DISTINCT: "is this a NEW build?" IS NOT "is this the RIGHT build?"** This row and its staleness checks (image id changed, timestamp moved) answer only the first. **⛔ AND "THE ARTIFACT" INCLUDES THE FILESYSTEM AROUND YOUR SOURCE, NOT ONLY YOUR SOURCE — the case with no staleness in it at all.** A **bind mount** makes your code live and leaves **its dependencies elsewhere**: a named `node_modules` / `vendor` / `site-packages` volume is populated from the image **on first use only**, so the source is correct, current and byte-identical to your tree while the tree beside it is months old. **Resolution, version and presence claims must be measured INSIDE the runtime the feature uses** (from inside it — e.g. `<runtime-exec> <resolve-check>`), never in your host shell — **a host check that passes is evidence about the host.** ⚠ The vocabulary of the rest of this row (image id, digest, timestamp, "rebuild") gives a reader nothing to match on here, which is why it is stated in its own words. **Where a build file has more than one leaf target, also assert something ONLY THE INTENDED TARGET PRODUCES** — a file that exists in one and not the other. *(Appending a `dev` stage to a Dockerfile silently repointed production, because a Dockerfile's default target is its LAST stage: the production build command then built `dev`, tagged it as production, exited `0` in one second and printed "Built". **The image id changed — the build genuinely was new, and new of the wrong stage** — so every staleness check passed. Caught in one line by asserting the image CONTAINED a source file it should have. Corollary rule: **a new stage goes BEFORE the stage that must stay default, never after; position is the only control and there is no directive for it.**)* Record your stack's form of the guard in your durable learnings home. |
| 2 | **FIXTURE VALIDITY — can this fixture physically EXPRESS the observable?** | **The fixture can be the bug, and it reads exactly like a broken feature.** Ask it once per fixture at prep: does the subject actually contain what the assertion needs to see? |
| 3 | **⛔ CAN A PERSON REACH IT? — the only trap that has ever shipped a broken phase here.** | Every gate can be sound and the deliverable still unusable, because **the gate reached the thing by a route no human has.** Four shapes, all measured on this project: **(a) THE WRONG SCREEN** — `create` and `edit` are different code paths, and a gate that mounts against a **seeded record** has said nothing about the screen a writer starts on. Name the VIEW, not the surface; if your arm loads an existing document, write `covers: edit view only` and say which view is uncovered. **(b) NO ENTRY POINT AT ALL** — a record, a validator, a renderer and 71 green assertions can ship with **no control that reaches them**. For every Scope line naming something a person *does*, name the step that builds their way in; the entry point is a DELIVERABLE, not an implication of the entity. **(c) AN UNREACHABLE PRECONDITION** — a refusal a smoke asks a human to observe, whose refused state an earlier validation makes impossible to produce. The rule is real, the observation is not: record it `enforced-but-unobservable`, name the entry path it *does* guard, and **keep it out of the smoke**. **(d) THE WRONG INSTRUMENT** — see the pointer clause in `execute.md` §Verify before edit. |

### Can this gate FAIL? *(design the gate before you run it)*

**RED-demo a gate that guards something which has ALREADY BROKEN ONCE, or when the lead asks. Not by default.** Everything below is how to run one when you do. A gate whose **fixture can't express the defect at realistic scale**, or whose **proof lane ≠ the feature lane**, is **structurally unfailable** and will certify a feature that does not work. (memory `feedback_gate_must_be_able_to_fail`.)

| RED-demo mechanic | When to use it |
|---|---|
| **(a) Stash-retrofit** | Authored tests + fixes in one batch → `git stash push -- <fix files>` (tests stay) → build → run the new slices RED → `stash pop` → gate GREEN. **Script it in one `/tmp` script so the pop always runs.** |
| **(b) ⭐ The artifact under test is CONTENT** (a fixture, a golden, an article) rather than source | **`git checkout <pre-fix-sha> -- <content-path>`, re-run the gate, restore under an always-run `trap`.** The **strongest and cheapest** demo available — it fires the guard against the genuinely-broken **historical** artifact, not a reconstructed break, and costs *seconds*. **Reach for it whenever the defect lived in content.** |

**Name which mechanic you used in the Execution Log.**

**⛔ Restore discipline — the neuter-and-restore hazard (where the whole change silently disappears).**
- **⛔ THE NEUTER MUST ASSERT ITS OWN MATCH COUNT — this doc's own default mechanic is the one that fails silently.** A `sed` that matches **nothing** exits `0` and prints nothing, and in an arm that silence is **worse than a wrong edit**: the artifact is unchanged, the gate comes back fully **GREEN**, and the green-arm bullet below then instructs you to write that up as a **discovery**. So the doc's most emphatic interpretive rule points straight at a **fabricated finding**. Use a literal-replacement script that prints `MISS` and **exits non-zero on no match**, or follow the `sed` with a verify `grep`. The symmetric inverse `sed` remains correct for the **restore**, which is verified by `git diff --exit-code`.
- **Default restore = a SYMMETRIC inverse-edit** — `sed` the neuter in, `sed` it back out, both in ONE `/tmp` script under a `trap`. **NEVER `git checkout -- <file>` / `git restore <file>` to undo a neuter on a file carrying UNCOMMITTED work** — they revert to HEAD and discard your *entire* uncommitted change, not just the neuter.
- **`git stash` only when the fix is fully committed AND adds no symbol the new tests reference** — stashing a fix that introduces an enum/symbol the tests use breaks test *compilation*, a build-fail masquerading as a RED. When the fix adds such a symbol, keep the declaration and **neuter only the load-bearing LOGIC in place** (sed a unique substring to a no-op).
- **Fix completes an ALREADY-COMMITTED WIP test set?** Commit the fix first, then RED-demo via source-neuter + restore — not stash.
- **⛔ IF THE ARM MUTATES SCHEMA OR RUNTIME STATE RATHER THAN SOURCE, THE TRAP IS NOT ENOUGH AND `git status` CANNOT SEE THE DAMAGE.** Everything in this block is written for **source**, and none of it reaches an arm whose neuter is a `DROP NOT NULL`, a revoked grant, a flipped feature flag or a seeded row — where the hazards are different and worse: **a source neuter is undone by the trap; a SCHEMA neuter SURVIVES THE SESSION.** A killed demo leaves the live database permissively typed, invisible to every working-tree check, and the drift gate is then red for a reason that looks like a bad migration. **Restore inside the trap AND READ THE STATE BACK** (`information_schema`, a probe query) as the arm's last act, **printing what you read** — the trap having run is not evidence the restore took. **And state the precondition that makes the mutation safe** — an empty table, a torn-down fixture — **because a schema arm that is safe today is destructive the week after**: a `SET NOT NULL` succeeds on a table with zero rows and fails on a populated one, and a demo that cannot run is better than one that half-runs. **Re-run the drift gate before you commit.**
- **Run RED-demos EARLY in the run, not near a ceiling** — any RED-demo that reverts a *tracked* file (stash or `git checkout <sha> -- <path>`) triggers a full-file context injection (~1k lines / ~30k tokens) when the harness re-reads it; that cost lands worst right before a context ceiling.

- **⛔ THE ARM MUST PROVE ITS NEUTER REACHED THE ARTIFACT UNDER TEST.** A neuter that fails to compile — or a build that fails for *any* reason — leaves the **previous artifact running**, and a health check or container-status poll passes happily against it. The arm then reports **GREEN**, which reads as *"the control is unfailable"* rather than the truth, *"the arm never ran"*. **Check the build's exit status and abort the arm on failure**, and where the neuter is source, **typecheck the neutered tree before building** so a bad neuter is loud at the cheapest point.
- **⛔ A RED DEMO HAS TWO SUBJECTS — THE ASSERTION AND THE HARNESS. Run the discriminator on BOTH, and ask it two-sided: can it fail, AND can it pass?** A verification that inspects a **built** artifact must key on something that **survives the build** — a string literal, a digest, an **image ID** — never source structure the compiler rewrites. Record the stack-specific form in your durable learnings home.
- **⛔ BEFORE WRITING UP A GREEN ARM AS A FINDING, CONFIRM THE NEUTER CHANGED THE ARTIFACT.** A no-op neuter and a genuinely-enforced-elsewhere property produce **byte-identical gate output**, and this bullet is what turns the first into a confident false claim. The precondition is stated here, bound to the bullet it protects, rather than three bullets up where it did not reach the reader who needed it.
- **⛔ AN ARM THAT STAYS GREEN IS NOT A FAILED DEMO — IT IS A MEASUREMENT, AND IT IS THE HIGHEST-VALUE RESULT THIS METHOD PRODUCES.** It says the property is **enforced somewhere other than where you thought**, and that *somewhere* is a finding: **name it, log it in the Execution Log, and check whether the redundancy is deliberate.** ⛔ **Two enforcers is the COMMON case wherever a framework mirrors a table** — versions, drafts, audit copies, caches — **so neuter ALL of them or you are demonstrating nothing.** **⛔ THIRD CAUSE, AND IT IS THE ONLY ONE THAT LEAVES A REAL HOLE: THE SUBJECT CANNOT EXPRESS THE FAILURE.** The two causes above both mean the property is enforced **twice or elsewhere** — the system is fine and you found a redundancy. This one means the arm was right, the gate was right, and **the fixture cannot reach the branch under test**, so that branch has **ZERO coverage and always did**. **Diagnose it by asking what the subject would have to CONTAIN for the arm to redden, then checking whether it does** — pre-smoke row 5, asked *after* the fact rather than before. **The fix is never to loosen the assertion; it is to give the branch a subject** — usually by extracting the logic to a pure function and asserting both branches there, which needs no seeded row and no stack.
- **⚠ A STANDING NEGATIVE CONTROL CAN REPLACE AN ARM, AND IS BETTER WHERE AN ARM IS EXPENSIVE.** If the gate can assert its predicate against a **known-negative subject already on screen** — a field of the wrong type, a collection without the feature, an unrelated row — **that control proves the predicate discriminates on EVERY run, needs no neuter, no restore and no rebuild, and cannot be forgotten the way a one-off arm's evidence can.** Prefer it wherever an arm would cost a rebuild; keep the arm where only a real neuter can reach the behaviour.
- **⛔ AND RECONCILE THE RED SET BEFORE BELIEVING IT — THE NEUTER IS APPARATUS AND CARRIES ITS OWN BUGS.** **Predict which assertions the arm should redden BEFORE running it, then account for every difference.** An arm that reddens **FEWER** assertions than predicted is more likely a **wrong neuter** than a weak gate. **The classic case is a partial-condition neuter** — one gated on a length, a count, an index — which fires on a subset you did not intend while the surviving green assertions are entirely correct.
- **⛔ A killed demo restores SOURCE and never the CONTAINER.** An interrupted arm's `EXIT` trap leaves a pristine tree over a **neutered artifact** — `git status` clean, `git diff` empty, HEAD sane, and the running app still misbehaving. On any resume into an image-baked project, **a clean git tree is not evidence the running artefact matches it**: verify the artefact or rebuild before trusting a baseline, or the next gate run's failures are indistinguishable from a real regression.

**⛔ CAN THIS GATE *DESTROY*? — the question this section never asks.** Everything above interrogates whether a gate can *fail*. A gate's **fixture seed and teardown run against the REAL system.** **Scope every teardown to rows the fixture itself created — never `delete *`, however empty the table looks today.** The table is empty exactly while you are writing the gate, and full the first time it matters. **A gate that damages the system it certifies is worse than no gate.**

**⚠ A RED-demo script exits NON-ZERO BY DESIGN** — the gate under test is *meant* to fail, so a build failure AND the intended RED both surface as exit 1. **Never infer outcome from the exit code on a RED demo; read the per-test log and confirm each RED is for the intended reason.** (Banner Rule 3's "trust the exit code when the load-bearing command is last" does NOT apply here.)

**⛔ Front-loaded a headless lane that FIXES a defect a later `⚠human` sitting was meant to show RED eyes-on?** You've spent that sitting's RED baseline. The eyes-on-RED half now requires running the **pre-fix artifact** — the stale-installed binary, or `git checkout <pre-fix-sha> -- <artifact>` — the installed-binary sibling of mechanic (c) above. **Bank it as an explicit sitting precondition at suspend; don't rely on install-lag to hand it to you**.

**⛔ AND THE MIRROR CASE — THE SAME CHECK RUNS IN BOTH DIRECTIONS. Before suspending with any `⚠human` item still pending, re-check what the steps you just landed did to that sitting's preconditions.** Front-loading can spend a RED baseline; it can just as easily **degrade the GREEN the sitting was meant to observe.**

**⛔ AND SAY SO WHEN A STEP MUTATED OPERATOR-FACING RUNTIME STATE** — a credential, a bootstrap account, seeded data. **The lead cannot diff runtime state, and no working-tree check will show it.** Name what changed **and how to restore or re-obtain it**.

**⛔ The DISCRIMINATOR — four tests, all of which must pass:**

| # | Test | Why |
|---|---|---|
| 1 | **Is the correct look visually distinctive at all?** | If not, the plan should have named a discriminator (debug paint / colored fixtures — `plan.md` §Sittings). If it didn't, **add one BEFORE the sitting**, not mid-sitting. |
| 2 | **Can the discriminator FIRE on its own fixture?** — *"does ANY control on this fixture visibly work today?"* | A discriminator that cannot fire is not a gate: a FAIL then reads as "the fix didn't work" with **no route to the truth**. |
| 3 | **⛔ Does it prove the fixture took YOUR lane?** — **the right pixel is NOT a PASS** | Test 2 catches *"the fixture can't respond"*; it does **not** catch **"the fixture responded for the wrong reason"** — the **false PASS**, which is worse than a false FAIL because nothing prompts you to look. Mirroring the Premise-Proof gate's lane-naming: **name a log/trace predicate proving the fixture traversed the feature's branch, and score `PASS` only when the pixel AND the predicate agree** — e.g. *"PASS = glows magenta **AND** `master-resolve … outcome=1`"*. **Corollary: if the expected look is achievable by ANY pre-existing path, the discriminator is INVALID** — pick a look impossible in the pre-fix world, or pin the trace predicate. |
| 4 | **⛔ Does the fixture conform to the PRODUCT MODEL, or only to the asserts you CHOSE?** | A de-risk whose asserts are **author-selected** can be **11/11 GREEN on a structurally-forbidden artifact** — nothing checks the object→mesh→material SHAPE unless you make it. Validate the artifact's shape against the spec, and **prefer a NEGATIVE assert derived from the spec's forbidden list** (`zero texture files of ANY kind`, not `zero Matter-named textures`). A green de-risk that asserts MECHANICS but not PRODUCT-MODEL CONFORMANCE manufactures false confidence — **worse than no de-risk** (`feedback_gate_must_be_able_to_fail`). |

**⛔ THE SAME DISCRIMINATOR FOR A HEADLESS *ASSERTION* GATE (HTTP / SQL / CLI — no pixels).** Every term in the table above is visual, so on a phase whose deliverable is ~80 HTTP and SQL assertions it reads as *not applicable* — and it is not: it is the **same four tests in another vocabulary**. Its two operative forms:

- **(a) PAIR EVERY REFUSAL WITH A POSITIVE CONTROL** — an otherwise-identical request that must **SUCCEED**. This is test 3 (*did the fixture take YOUR lane?*) in assertion form. **A refusal alone is satisfied by a malformed request, a wrong id, a broken credential, or a validator that refuses everything.** It costs one extra assertion and is the cheapest high-yield discipline in the whole gate.
- **(b) ⛔ NEVER LET AN ASSERTION'S SUBJECT BE STATE THE PROBE ITSELF CREATED — a row the fixture seeded, OR A PAGE A PREVIOUS STEP OF THE SAME PROBE MUTATED.** The fixture's apparatus exists to make *other* assertions possible; an assertion that reads it is testing the fixture. Prefer a subject created by the run's own exercised path. **On a browser probe this means every INTERACTION — a click, a form fill, an expand — runs AFTER every read that shares its page load**; otherwise a later assertion is measuring the aftermath of your own input.
- **And an assertion phrased as an ABSENCE** (`X not in Y`, `count === 0`) **must also assert `Y` is non-empty**, or it passes hardest when the thing it guards is gone.
- **(c) ⛔ NEVER ASSERT AGAINST A RESPONSE THAT ECHOES YOUR REQUEST.** A create/update reply commonly returns the submitted document, so **any assertion searching the whole reply for a value YOU SENT passes whether or not the system did anything.** Scope such an assertion to **the branch that cannot contain your input** — the error envelope on a refusal, never the success body — and make the wrong branch an **explicit FAILURE** (*"the write was not refused, so there is no refusal message to name X"*) rather than a silent miss. *(A gate asserted that each refusal **names the offending token**, searching the serialised reply for e.g. `textStyle`. With enforcement disconnected **entirely**, **11 of its 12 token assertions kept passing** — an acceptance is a `201` echoing the submitted document, so every offending token was present by construction. The gate could not have reported green overall, because each token assertion was paired with a refusal assertion that did go red — but the token assertion, the one carrying the "refused for the RIGHT REASON" claim, was **inert**, and a later refactor could have left it as the only cover for a rule. Scoping it to an actual refusal moved that arm from 14 red to 25. **Review would never have found this; only the arm that broke the thing hardest did.**)*
- **(d) ⛔ AN `if`/`else` WHOSE BOTH BRANCHES RECORD A PASS IS NOT A GATE.** The tell is an `else` that asserts the **absence is acceptable** — *"absent rather than empty"*, *"no rows, which is fine"*, *"not configured, so nothing to check"*. **The failure state then selects the branch that blesses it**, while the code reads as a careful piece of work that thought about both cases. **Assert the PRECONDITION as its own assertion** (*the subject has a byline at all*) **and then assert the property against it**, so the vanishing case reds on the precondition instead of choosing its own verdict.
- **(e) ⛔ AN ASSERTION THAT CAN ONLY EVER BE TRUE — because the world cannot currently produce its failure, AND THE WORLD IS EXPECTED TO CHANGE. KEY IT TO THE CAUSE, NOT THE ABSENCE.** Ask: **what would have to change in the world for this assertion to become WRONG — and when it does, will it go RED, or GREEN?** An assertion that stays green while the correct behaviour changes underneath it **has silently turned from a guard into a DEFENDER OF THE DEFECT**. ⚠ **It passes the *can-this-gate-fail* test, because it can — just never in the direction that matters**, and unlike (a)–(d) **it has no tell at all: everything is green and stays green.** **Read the cause LIVE** — the model, the config, the flag — and let the assertion **invert itself**: *while X does not exist, Y must be absent; the moment X exists, Y is owed.* That is also the only form of "carry this obligation forward" that **cannot be forgotten**, because a `DEFER:` line, an issue and a comment all depend on somebody reading them.

**⛔ NAME THE FAMILY, BECAUSE FINDING YOUR CASE IN IT IS THE HARD PART: (b)–(e) ABOVE, PLUS THE GREEN-ARM CAUSES BELOW, ARE ALL *WAYS A GATE CAN BE GREEN ABOUT NOTHING*.** They differ only in **what** is missing: the *subject* is contaminated (b) · the *response* echoes your request (c) · **both branches pass** (d) · **the world cannot produce the failure yet** (e) · the *fixture* cannot express it · a *second enforcer* is doing the work. **When a gate feels too easily green, walk the family rather than re-deriving from first principles** — three separate runs reached the right answer by reasoning from scratch and only afterwards recognised the rule they had re-invented.

- **⛔ AN ASSERTION MUST PRINT WHAT IT MATCHED, NOT ONLY ITS VERDICT — identity, not pass/fail.** In the recurring failure below the *mechanism* assertion is **correct** and the **subject** is wrong, and **no amount of re-reading the assertion reveals it, because the assertion is true.** What reveals it is printing the matched thing's identity: its text, its `tagName`, its `className`, the stored row's own value. The cost is one string per assertion and it is the only thing that has ever caught this class.

*(One run wrote this exact failure three times after reading and agreeing with the table above: an "expired session does not authenticate" assertion passed **twice for reasons unrelated to expiry** — first a `sid` of the literal string `"undefined"`, then a derived signing key making it a bad-signature refusal — and would have stayed green with expiry enforcement deleted entirely; a "creating an account writes a `user.created` row" assertion passed **with every writer neutered**, because it read a row the fixture hand-seeds; and a "a role change emits ONE row" assertion passed reporting `0 row(s) for three acts`. **All were caught by RED demos and positive controls; none by review.**)*


**⛔ A GATE CAN BE **BLOCKED** AS WELL AS PASS OR FAIL, AND ON A SHARED BOX THE BLOCKER IS USUALLY FOREIGN DATA.** *(Three occurrences, three gates, each inventing the machinery from scratch.)* An abort-the-whole-tree gate — one bad row kills the run — meets a row another session left behind, and `execute.md` is explicit that **those rows are not yours to delete**. Give the gate a **third outcome**, and note that only the last of these four is written down anywhere else:

1. **Catch the abort** rather than letting it kill the run.
2. **DISCRIMINATE** — a blocking subject the gate **OWNS** is a real red; only a **foreign** one is `✗ NOT RUN`.
3. **NAME the blocking subject** in the output, so the next reader can act on it.
4. **⛔ CONDITION THE GATE'S CLOSING SUMMARY ON WHAT ACTUALLY RAN.** This is the load-bearing one. *(A gate printed `NOT RUN` correctly for its blocked leg and then closed with *"…and the archive carries that referent's descriptive and commercial identity beside the story that points at it"* — **a green that is also a lie**, in the one line a future reader is most likely to read and least likely to check. The author caught it re-reading their own output; nothing prompted it.)* **A summary sentence claiming a leg that did not execute is the most durable lie a green run can tell.**

⚠ **The blocked-row disposition itself is a LEAD call, not the gate's** — one such block resolved to **repair, not delete**, on a lead ruling. And note the repair can be wider than it looks: repairing only the main row left the gate failing **identically**, because the version row was the real blocker.

### Test sequencing and suite scope

| Rule | Detail |
|---|---|
| **⛔ Smoke-FIRST, regression-tests-AFTER** (behavior-goal phases) | (a) prove the behavior at the live smoke → (b) **THEN** write the regression tests, live-shaped, RED against the now-*known real* failure. Two hard rules: **a test that has never been RED against a real broken state is not yet a proof**, and **one live-shaped end-to-end test beats N isolated-layer tests that can all stay green while the chain between them is broken.** This re-orders the RED-demo discipline, it doesn't weaken it. (memory `feedback_smoke_first_then_tests`) |
| **Behavior-preserving phase?** | Goldens byte-unchanged is necessary but **NOT sufficient** — also verify the non-golden observables §6 enumerated (error/exception-type parity, log-line content + timing, lazy/eager evaluation ordering). **Go looking for these** — they're where a "no-op" restructure silently regresses. |
| **Capture evidence as you go** | Tail *and keep* the logs (op results, events fired, warnings + triage) — that becomes the evidence in your **handback** (`execute.md` §Handback). Don't reconstruct from memory. |

### Running the `⚠human` sitting

| Rule | Detail |
|---|---|
| **A `⚠human` sitting OPENS with the LAUNCH, not with code** | First action is the launch + arm the log monitor. Even a `⚠human-codev` item writes UI/code **reactively** against what the smoke reveals — *"carry on / do the sitting"* defaults to **launch + tail**, not *edit code*. |
| **⛔ ONCE THE SITTING IS LIVE, THE STACK UNDER REVIEW IS FROZEN TO YOU** | **No seeds, no probes, no fixture teardowns, no diagnostic writes against the surface the human is judging.** Diagnostic work during a sitting either **waits**, or runs somewhere that is not that surface. If you genuinely must touch it, **say so before you do**, so a symptom they hit is attributable in one message instead of three. ⚠ **This is not carelessness waiting to happen — it is structurally invited:** the sitting is exactly when the executor has spare cycles and a natural urge to keep working, and `execute.md`'s front-load carve-out actively encourages draining autonomous work in parallel with `⚠human` steps. That is right in general and **actively wrong for work that mutates the sitting's own stack.** The existing runtime-state rules do not cover this: both directions they describe are **agent-to-agent** (state a sibling left me, state I leave a sibling); this is **agent-to-HUMAN, in real time, on the surface they are actively judging.** |
| **⛔ THE `▶` HANDING OVER A SITTING CARRIES THE SITTING SCRIPT ITSELF, NOT A POINTER TO THE BAR** | A URL plus a reference to the acceptance clauses technically satisfies "a call to action" and **leaves the human with nothing to do**. What they need is an **ordered script**: what to open, what should be on screen, the question to answer at each step, what a miss looks like, and **which single clause is genuinely subjective**. Write it before you hand over, not after they ask. |
| **⛔ TERSE per-step cadence — the lead is WAITING at the machine** | Emit **only** `Testing: <X> · You do: <Y> · (I read the log)` per step — **no tables, no multi-option menus, no essay.** **Lead with the single most load-bearing test; if it FAILS, stop** — the lead has zero interest in testing 20 other things when the main one fails. Claim-ledgers and result tables belong in the write-up, **never the live drive.** |
| **Open with a two-line CLAIM LEDGER** | What is **PROVEN** (a gate actually ran) vs what this sitting **TESTS** (hypothesis / parity-level claims). Never let a parity-pinned exoneration read as a live-validated fix. |
| **A REPAIR/RECOVERY smoke CONSUMES its own fixture** | Every remap/clear/heal the lead drives *fixes* the broken state the next round needs ⇒ **budget N re-authors for N rounds**: keep a pristine broken copy to re-open per round (or a tiny re-break script). Don't hand-re-derive the broken bindings each time. |
| **Don't volunteer a suspend MID-sitting** | A live sitting is a **cohesive unit** — wrap at the sitting boundary and bank findings first, even if a context band fires mid-drive. **Banking includes the Resume-block supersede:** a run that ends at/after a sitting with NO formal suspend still owes it — at minimum stub the stale header `⚠ superseded by Exec-Log E<N>` before ending; a LIVE-labeled stale block drains the next resume toward the wrong gate. |
| **But a FIRST-ever eyes-on gate is a likely SESSION boundary — budget it as one** | The Premise-Proof rules already predict the sitting will spawn a repair-loop code cycle (`execute_repair.md`); that cycle **plus the close** is a *session's* worth of work, not a tail. Drive the smoke, bank the repair findings + scope into the doc, and **recommend resuming the repair cycle (and the close) fresh** rather than draining smoke → repair → close continuously. |
| **⚠ THE LEAD WILL PROPOSE CAUSES MID-SITTING — DO NOT DEFER TO IT AND DO NOT ARGUE IT** | **Convert it to the cheapest DISCRIMINATING MEASUREMENT and run that.** They are at the machine and are often right; you have the instruments. *"Your reading predicts X, mine predicts Y, here is the one probe that separates them"* costs one turn and settles it. The cadence rules above cover **driving** the human and the divergence table covers the lead **ruling** — neither covers the lead **hypothesising**, and the pull is to honour it (a detour) or to defend your own (an argument). *(In one sitting the lead offered two causes: the first was wrong and honouring it would have cost a detour; **the second was correct and beat the agent's diagnosis to it.** Both were resolved by one header and one URL.)* |
| **Cheap ready artifact before heavy prep** | When the plan splits a human gate into a cheap ready artifact + an optional heavy live-smoke, **surface the cheap artifact's REAL output inline FIRST** (`Read`/show the actual file) before kicking off the heavy prep — and label the prep unambiguously (*"this build is prep for the live smoke; the smoke launches after"*). Don't background a multi-minute prep with a bare "I'll report when it lands" while a ready deliverable sits unshown. |

### Scoring it: what a PASS actually proves

- **The manual smoke is the SEMANTIC gate, not a victory lap.** Automated parity/golden gates prove the change *matches the plan*; the human smoke proves **the plan was right** — a parity test cannot validate its own premise. So expect the smoke to **legitimately re-open a "done" step → that's the repair loop (`execute_repair.md`), not a derail.**
- **Report the gate LEADING with the lead's observed outcome — traces explain, they never overturn the eyes-on verdict.** *"Wire values matched"* is not a win while three flows fail on screen.
- **For eyes-on / visual-only gates** (a render check whose log markers are absent by design), **the driver's verdict IS the gate result** — don't block on a log signal that doesn't exist.
- **A diagnostic log marker proves the code REACHED that line — never that the visible outcome occurred.** For a visible gate only what the eye sees (or a pixel/DOM assertion) is proof — **never write "verified live" off a marker**.
- **⛔ An eyes-on PASS proves what the eye was POINTED AT — never that the phase's GOAL is met.** **Ban unqualified victory nouns** ("zero defects", "complete", "fully working") from smoke docs and `🎉` bodies; **require the scope clause**: *"all N defining observables pass **as driven on the dev rig** — NOT a claim about delivery / packaging / another machine."* The smoke doc's result table is **durable and is what the next phase will trust**, so grep **IT** for completion claims against the open DEFER list, not just the commit body.
- **A phase whose deliverable is *speed* can make its own `⚠human` gate un-exercisable** (a load cut to ~0.3 s leaves no window to click Cancel) — the **green headless proof is then the gate of record** (surface it *"verdict-by-headless, lead-accepted"*). Flag such verdicts at plan time (`plan.md` §Sittings) when foreseeable.
