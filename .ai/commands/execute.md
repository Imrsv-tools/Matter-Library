Execution driver for a phase. Runs **stages 2–4 of the Phase Workflow — Build → Try → Strengthen** — and hands back. It does not close (that is [`execute_close.md`](execute_close.md)).

**⛔ THE MEASURE OF THIS RUN IS HOW LONG UNTIL THE LEAD CAN CLICK THE THING. Target 60–90 minutes.** Missing it is a **scope alarm** — say so, and say which: phase too big · loop too slow · supporting work displaced the first step. It is never a cue to certify harder before showing him.

The argument is the unit — a phase (`19` → `docs/Planning/Phases/Phase19_*.md`) or an Issue (`#<n>`). **`/execute` itself is the approval; do not ask.** Flip the status to `IN EXECUTION` and go.

## ⚠️ THREE RULES THAT KILL THE PROMPT STORM — READ FIRST

These prevent ~90% of permission prompts, and they lose to faster reflexes when buried.

1. **NO capture-tails. EVER.** Never append `; echo "…=$?"`, `&& echo …`, `|| echo …`, or `> file` to a command — **including inside a `/tmp` script's body.** That tail, not the command, is what prompts, and it is never informationally necessary: the Bash tool returns a non-zero exit as an error, and gates print their own PASS/FAIL. To see a test's true crash signal, **redirect to a `/tmp` log and Read it** — never pipe to `head`/`grep` and inspect `$?`, which gives you the *pager's* exit `0` and masks a real SIGSEGV.
   **⛔ AND NEVER BUNDLE A FILE WRITE WITH ITS VERIFICATION IN ONE CALL.** From outside, an edit to a tracked file is indistinguishable from a status check, and the lead's only options are accept-blind or interrupt. **Land the write; verify in a separate call.** This is a *legibility* rule, so it holds regardless of permission mode, and it matters most for an edit the plan did not schedule — the one that most needs a reviewable line of its own.
2. **Literal paths, no `$VAR`, no `cd`.** One statement, absolute literal paths, no `$(...)`, no backticks, no redirects outside `/tmp`. Inspecting git is where this bites: use `git -C /abs/repo …`, **never** `cd repo && git …`. Repeat the literal path rather than holding it in a variable. Push prompts **by design** — push is lead-gated; that friction is expected.
3. **Long ops → background, then END THE TURN.**
   **⛔ TRY THE DIRECT SINGLE STATEMENT WITH `run_in_background: true` FIRST.** A single analysable command (one binary, literal flags, absolute paths — a build or a stack-up invocation) backgrounds fine, while `bash /abs/script.sh` is **opaque to the classifier by construction** — so on a long-but-simple op the script is the *less* likely shape to be allowed. **A denial of `bash script.sh` is usually a denial of the wrapper, not the operation: re-issue it as one direct statement before handing the lead a `! bash …` line.**
   Where a script genuinely is right (several statements): write `/tmp/p<NN>_<step>.sh` redirecting its own output to a log, invoke it as `bash /tmp/…` (a Write-created script is not `+x`), background it. **⚠ The load-bearing command must be the LAST line, and if the script has MORE THAN ONE load-bearing command, `set -e` IS MANDATORY** — without it the exit code is the last lane's alone, so an earlier `typecheck` failure is discarded and the notification reports "exit code 0" over a red build. **`set -x` traces; it does not fail.**
   **⛔ THE TRIPWIRE: if you are about to check a backgrounded task you have already checked once, you are in the loop. End the turn.** A no-op call (`true`, `sleep 1`, an empty `ls`) is the same violation — **if your next tool call has no result you intend to read, you do not need a tool call.** The completion notification is your wake signal.
   **⚠ The one condition that voids the tripwire: the wake signal is broken.** A task reporting `stopped`/`killed` with no completion record will never notify — relaunch it detached and wait on a `Monitor` until-loop whose pattern matches the **failure** signatures as well as the success one. An until-loop must assert its subject set is non-empty; a loop whose filter matches nothing runs to exhaustion and exits `0`, indistinguishable from a clean finish.

   **⛔ A SCRIPT YOU HAND A HUMAN TO RUN IS A DIFFERENT SHAPE FROM A BACKGROUND LONG-OP — AND SECRETS ARE WHY.** *(Any operator script `/execute` authors: provisioning, custody drills, destructive confirmations.)*
   - **Prompt from `/dev/tty`, never stdin.** Under any wrapper that doesn't attach a terminal to stdin, `read` hits EOF, `set -e` fires, and the script **exits silently** — prompt printed, nothing created, exit 1, no error. `|| true` every `read` so EOF can never become a silent `set -e` exit.
   - **Test the terminal by OPENING it:** `{ : < /dev/tty; } 2>/dev/null || fail "…"`. A `[[ -r /dev/tty ]]` test **passes where the open fails**.
   - **Never ask the lead to paste a live secret into a command line or into chat**, and never pass one as an argument or an exported variable — it lands in the transcript and in shell history, and a bracketed-paste control character can split it across a command boundary. Route it through a tool that prompts on the terminal itself, a script that prompts on `/dev/tty`, or a file the lead writes.
   - **If a secret reaches the transcript anyway — say REVOKE first, continue second.** That includes one a *vendor* printed (a root password in provisioning output), not only one you asked for.

## Before you touch anything

1. **A Brief is present** in the working doc (Outcome · first human test · in/not-now · reuse check · lane · step list · build map). If it is missing, stop — the unit is not ready.
2. **⛔ RECORD THE TREE, DO NOT JUST PULL.** Write down `branch`, `HEAD`, `git status -s`, and who else is working here. **This tree is shared and dirty by design.** Pull only when it is safe to.
3. **⛔ EVERY STEP MUST NAME ONLY TARGETS THIS PHASE OWNS.** Walk the step list and check it *before* you start — a step that fails this is **structurally blocked**, not merely at risk.
4. **Expect prompts.** This box runs `permissions.defaultMode: auto`, not a bypassing mode. The classifier denies destructive, outward-facing and credential-shaped commands regardless of the allowlist, and compound commands remain un-analysable. That is the environment working correctly.
5. **Outward-facing actions are lead-gated** — `git push`, network fetches, out-of-tree writes. A plan-time scoped grant IS the gate; do not re-ask per action.

## 2) BUILD

**⛔ FIND THE FASTEST LOOP THAT STILL PROVES THE THING — BEFORE you start iterating, not after.** Split the work into what genuinely needs the full stack and what does not. A pure module runs in seconds; a full production rebuild takes minutes. **Do not rebuild the production artefact to see a change** — if your stack has a hot-reload or watch path, that is what it is for, and if it does not, finding the cheapest proving loop is itself the first thing to do.
**⛔ AND RE-ASK THE MOMENT THE LOOP CHANGES CHARACTER** — most often when you stop *authoring* and start *diagnosing*. "Before you start iterating" reads as a once-per-run question; it is not.

**⛔ "IS IT UP?" AND "IS IT CURRENT?" ARE DIFFERENT QUESTIONS, AND A HEALTH CHECK ONLY ANSWERS THE FIRST.** *"Running"* reads as reassurance and says nothing about whether the running artefact contains your work. Two things answer the second: **(a)** compare the artefact's **build time** against your most recent commit — if it predates a step you are about to trust, stop; **(b)** assert, **from inside the runtime**, a source path the newest step created. **⛔ AND IF YOUR PROJECT HAS MORE THAN ONE WAY TO RUN — a production build and a hot-reload loop, say — A RESUME INHERITS WHICHEVER THE LAST SESSION LEFT UP.** Find the tell that distinguishes them (an image tag, a port, a process name), and record it in `LOCAL_DELTAS.md`; *"it is up and healthy"* is true of both. *(One run took a nine-lane gate baseline against a build missing nine of its own phase's steps, and found out incidentally.)*

**⛔ AND WHERE A PRODUCER PUBLISHES THE ARTEFACT, THERE IS A THIRD QUESTION AND NEITHER COMMAND ABOVE REACHES IT: *has my change reached the thing a reader actually loads?*** *"The build succeeded"* and *"the reader can see it"* are different claims whenever something other than the process you restarted is responsible for publishing. **Find the served tree and diff it against your build output.** ⚠ **A publisher typically has a trigger and a lock, and both can strand you silently**: a long-lived watcher may hold the publish lock for its whole life (so a manual publish is refused, correctly) while waking only on a marker your kind of change never moves — so an edit has *no route to the live edge at all*, with every process reporting healthy and current throughout. *(Two lead round-trips, one per step, each ending with the lead hand-moving the marker. The first cleared **by luck** — a sibling session's write moved it while the run waited — which is worse than failing, because it made the mechanism look like it worked.)* **If your project has a producer, record its trigger, its lock and its marker in `LOCAL_DELTAS.md`** — all three, because knowing about the lock does not help if you cannot name what wakes it.

**Restate the phase's `Outcome` in one sentence before you start draining steps.** If your "done" claim is about a mechanic, name the user-facing thing it delivers. **Drain the critical path to the first human test FIRST, not local polish.**

**⛔ SPLIT THE PHASE'S OWED ITEMS INTO *RULINGS* AND *WORK* BEFORE THE FIRST STEP, AND PUT THE WORK IN THE STEP LIST.** A Brief heading *"decisions this phase owes"* invites you to treat every one as a question for the lead. Some are: a URL shape is a sentence. Others are a decision **and** a change — a freshness model, a retirement story, a default — and those need building, not just answering. **Ask of each: "when the lead says yes, is there anything left to do?" If yes, it is a step.** *(One phase's third owed item was a freshness model. The lead's delegation let the run **answer** it without noticing it also had to be **built**; it never entered the step list and surfaced at the close, after the `🎉` was being drafted.)*

**⛔ IF THE PHASE'S `Outcome` IS A LIST OF ACTS A PERSON PERFORMS, THE UNIT OF WORK IS AN ACT — NOT A STEP — AND THE LEAD DRIVES EACH ONE BEFORE THE NEXT BEGINS.** Walk one complete user-facing act, together, fixing what it turns up, then start the next. **Do not drain the plan's steps and hand over a finished phase for one closing sitting.**

**⛔ ASK WHETHER THE LEAD IS AVAILABLE BEFORE ASSUMING THEY ARE NOT.** A present lead is the cheapest instrument on the project. *(Five hours and seven agents into one phase, with eleven of twelve steps landed and every gate green, the lead opened the admin and hit a dead page. Their words: "I am ALWAYS here waiting to test and you never ask." The pivot drove five acts in ~90 minutes and found **nine defects — every one of which had survived ~120 green assertions.**)*

**The front-load carve-out below is written for an ABSENT lead, and that is the only case it serves.** When the lead is not available, you may reorder within step dependencies to do autonomously-completable work ahead of human-gated work, and batch the sittings. **When the lead is available, that ordering is wrong** — it is what produces a finished phase nobody has ever used.

**Native capability first.** Configure before you write. Every custom layer must be able to name the native behaviour it replaces and the gap that justified it. *"We may eventually need more control"* is not a gap. **⛔ AND AN EVALUATION THAT REJECTS THE PACKAGE MUST ALSO REMOVE IT** — install it, read it, decide, then **uninstall and verify the manifest and lockfile are byte-identical to their committed state.** *"Test it, don't assume"* reads as finished at the verdict; it is not. An unused dependency is supply-chain surface, and a lockfile change you did not intend is a rebuild somebody else pays for.

**⛔ CLAIM LIVE NAMESPACE VALUES AT THE MOMENT YOU USE THEM — never bank one from a plan or a doc.** Version constants, gate ids, entity-id prefixes and migration ordinals are centrally allocated and a sibling phase moves them under you. Read the live value; a plan's figure is a hypothesis with a date on it.

**⛔ BEFORE THE FIRST COMMIT OF A STEP, RUN THE REPO'S ALWAYS-ON GATES — typecheck, lint, format — not only the phase's.** They appear in no phase's verification list *because they belong to no phase*, which is exactly why they go unrun. **A formatter failure is invisible to every phase gate, lands green locally, and reddens CI for everyone until someone runs it by hand.** *(One file failed Prettier from the evening it landed; CI was RED on `main` for ~10 hours, through a phase close and a retro, and nothing said so.)*

**⛔ BEFORE COMMITTING A STEP THAT BUILDS A MECHANISM, NAME THE CONTROL A PERSON USES TO REACH IT — AND THE ROUTE THAT CARRIES THEIR REQUEST TO IT.** If either is "another step", say which. If either is "none", **the step is not done**. **An endpoint with no button and no route is not a deliverable, however many assertions cover it.**

*(One step shipped a private-preview lane — signed token, minting endpoint, unauthenticated render route — on 26 green assertions, with **no control in the admin that called the endpoint** and **no path through the edge**, so every minted link answered `403`. The Outcome said "through the admin, without developer tooling"; the act was performable only with `curl`.)* **⚠ The ROUTE half is the one no gate can see** — every one of those 26 assertions talked to the app on loopback, so the edge was never in any assertion's path. A check that lives at test time cannot catch this: by then the step is long committed.

### Commit discipline

**Stage explicit paths** (never `-am`/`-A`), **commit with explicit paths** (never a bare `git commit`), `git add` a new file before its first explicit-path commit, and add a language's ignore file before first staging its directory. WIP-commit at sub-step granularity. **No Claude co-author trailer** — see `.claude/CLAUDE.md` §Git. The clean multi-path shape is `git -C /abs commit <p1> <p2> -m …`.

**⛔ AND KNOW WHAT THAT CANNOT SEE — THREE BLIND SPOTS, ALL OF WHICH HAVE BITTEN:**

- **A working-tree check cannot see a commit that has already LANDED.** `git status -s` catches another session's *uncommitted* work; that is its whole reach. At every suspend also run `git log --oneline` against the commits you made. **⛔ FILTER BEFORE YOU REACT: a landed commit touching `.ai/**`, `.claude/**`, `Methodology/**` or `AGENTS.md` is the Refiner, is expected, and is NOT a collision.** The process docs are not the project, and your briefing is the snapshot you read at start. **Notice, do not reconcile.**
- **⛔ AFTER ANY COMMIT, READ BACK WHAT YOU ACTUALLY COMMITTED — `git show --stat`** — reconciling the file list *and* the insertion count against the edit you intended. Every other check here is a **pre**-check, and in `git commit <paths>` the stage and the commit are one statement: a concurrent write to a path you named lands *inside* your commit, and only the post-commit diff can see it.
- **Foreign churn covers FILES only — it says nothing about shared RUNTIME state.** A step that resets a credential or reseeds data leaves nothing for `git status`. **You inherit runtime state as well as leaving it:** a gate asserting a whole-system property (*exactly one row*, *an empty table*) is structurally unpassable once another session leaves real data on a shared box. **That is a known INPUT, not a regression, and the rows are not yours to delete** — record which assertions are red and why. **⛔ Your own probe's residue is the hardest case, because it is indistinguishable from your own regression.** A probe that seeds rows must tear them down, and **if it borrows a shipped fixture's teardown it must create rows under that fixture's OWN prefix — read the teardown's predicate.** A teardown matching nothing exits `0` and reports success. *(A probe's two surviving articles moved a whole-system count, and the exporter was nearly diagnosed for the run's own litter.)* **⛔ AND A PROBE THAT TEMPORARILY MUTATES A ROW IT DID NOT CREATE LEAVES NO RESIDUE AND IS STILL DANGEROUS — the hazard is the WINDOW, not the leftovers.** On a box with a watcher, a timer or another session, *"I put it back milliseconds later"* is a race you are not refereeing. **Ask what else reads this row on a schedule before you write to it**, and prefer a row you created. If you must touch a live one, **check the published artefact afterwards** — the restore leaves the state clean, so no counter, gate or status line can tell you what the observer saw mid-window. *(A rename-read-restore against a live taxonomy term ran while a producer republished the site every 60s; a tick inside the window would have baked the probe's label into a published page's `<title>` and the counter would still have read clean.)*

### Verify before edit

| Trigger | Verify |
|---|---|
| **⛔ Your evidence that a hazard is CLOSED is a COMMENT or doc line CLAIMING a verification** | Re-run the check yourself. A comment is a claim about a past tree, not evidence about this one. |
| **⛔ You are committing code A GENERATOR wrote** — a migration, a client, a schema, a types file | Generated output is a **claim** about your project, not a fact. Read it. |
| **⛔ You are asserting — OR CLAIMING — something A PERSON SEES** — a rendered page, an admin surface, **or a URL you are about to hand the lead** | **Load it the way they will: a browser, with their headers.** A `curl 200` is evidence about `curl`. An unauthenticated `403`/redirect is not evidence the surface works. *(A run sent the lead to an admin URL on the strength of `curl → 200`. It was a dead page: the dev server refuses `/_next/*` to a host outside `allowedDevOrigins`, judging cross-origin from `Origin`/`Referer` — **which `curl` does not send**. The identical URL answers `200` to a script and `403` to a browser; nothing hydrated.)* **Sending the lead to a broken page costs their trust, not just a turn.** |
| **You are comparing a gate result against a baseline** | **Compare the SET, not the tally.** ⛔ **This fires hardest on a baseline YOU recorded, against a change YOU made** — a conditional field, a newly-guarded control or a narrowed fixture removes a subject from an enumerating assertion without moving its count. A self-recorded baseline feels authoritative in a way an inherited one does not. |
| **⛔ Editing an EXISTING function** | Read its **call site and its guard**, not only its body. A cited `file:line` proves the code exists, not that it runs. |
| **⛔ You are about to restate a COUNT / SET / VERSION / ATTRIBUTION** that a durable doc, a prior run, or your own earlier entry asserts about tree state | Re-measure. A stated count is a hypothesis with a date on it. ⛔ **AND "WHOSE DEFECT IS THIS?" IS A MEASUREMENT, NOT A PROPERTY** — a red inherited across resumes acquires an owner by repetition. **Name the observation that established it; if the answer is "a previous run said so", you have not got one.** For a gate, the cheapest such observation is the last CI run in which it was green. *(One red was attributed at `E2`, investigated at `E3`, restated at `E8` and again in a close commit — four restatements, zero re-derivations. CI falsified it four minutes after the push. ⚠ The phase's own note read "SAME COUNT, and the SET was verified member by member" — the set genuinely was, every time, and **the ownership claim rode along unexamined, protected by the diligence applied to the thing next to it**.)* ⛔ **AND A COUNT YOU MEASURED YOURSELF GOES STALE AT YOUR NEXT COMMIT, NOT AT SOMEONE ELSE'S.** The trigger reads as being about *inherited* numbers; it fires just as hard on one you took twenty minutes ago. **Re-run the measurement AFTER the last code change you intend to ship** — a green you took before a refactor is a green about the pre-refactor tree. *(A run measured 16 gate failures honestly, then wrote two hostnames into the JSDoc paragraph explaining why it had removed a hostname literal. CI returned 17.)* |
| **⛔ A GATE JUST WENT RED ON CODE THAT WAS GENUINELY WRONG** | **Append one line to that gate's header before you move on** — `// CAUGHT: <date> — <what>, (<commit>)`. `docs/ToolingConventions.md` §The gate registry owns the format and the exclusions (a RED demo is not a catch; a false red says `FALSE RED:`; a gate catching its own defect says `SELF:`). **This is the only moment the information exists cheaply**, and without it the question *"which gates earn their keep?"* is answerable only by archaeology — which for nineteen of thirty scripts could not distinguish *unrecorded* from *inert*. |
| **⛔ You are relying on a GATE** — one you inherited, one you are baselining, one a Brief says "still binds and widens" to your new surface, **or one you are ADDING A SUBJECT TO** | **READ WHAT SELECTS ITS SUBJECT, NOT WHAT IT ASSERTS.** Coverage is a property of the selector, and the selector is the half nobody opens. Three ways it lies, all observed on one day: **(i)** a selector reading **tree state** (*first match, newest row, whatever sorts first*) measures a **different thing** once you add content, and reports `PASS` in identical words — seeding a dozen records silently moved one gate's subject onto a different one; **(ii)** a structural selector can be **incapable of ever seeing your surface** — a gate enumerating `<build>/*/index.html` can never see a page at `<build>/index.html`, and the Brief asserting it "takes this page as a new subject" was simply false; **(iii)** a gate asserting a **whole-system** property has the **box** in its subject, so **a local red is a hypothesis about the box, not a finding about the code — and CI is the arbiter** *(one close classified six local reds; CI returned four of them green)*. ⇒ **A doc's claim that an existing gate covers something is a PRESENCE claim, so the absence-asymmetry row below does not protect you.** Never put such a classification in a close, a commit message or a handback as settled before CI has spoken. **⛔ (iv) A BROWSER GATE MUST CLICK, NOT MERELY LOAD.** Opening a page and reading the DOM is a `fetch` with extra steps — the defects a browser exists to catch live in what happens when a person *acts*. **Ask what the arm actually drives**, and be specific about the control: a browser gate that never clicks is *"green about a field nobody can reach"*, and one whose driving call is wrong for the element it names **throws, so its assertions never run at all and the gate reports on everything else** *(a `page.fill` against a `<select>` left five assertions dormant across every run of a gate that read as passing)*. **⛔ (v) AND IF YOU ARE ADDING A SUBJECT TO IT, ITS WORKFLOW PLACEMENT IS A CLAIM ABOUT ITS SUBJECTS' IMPORT GRAPH.** A gate on the fast/offline workflow is there *because* its subjects are pure — the gate's own header usually says so in as many words. **ONE TRANSITIVE IMPORT of the data layer costs it that workflow and NOTHING GOES RED:** typecheck, lint, format and the gate itself all stay green, and the first symptom is a CI failure in some later phase, attributed to whoever touched it last. **Read the header for the claim, then check your new subject's import graph against it** — an import added for one comparator call is enough. |
| **⛔ You are making data VISIBLE that no surface previously read** — a new page over an existing collection, a field promoted to a reader surface, a record type entering a feed | **Grep for what TRACKS reader-visible data and check whether your collection is in it** — staleness/cache sets, export allowlists, search indexes, feed subject sets, sitemaps. **Every such exclusion was written as a MEASUREMENT** (*"nothing reads this today"*) **and your change is what falsifies it.** ⛔ **The code naming the condition is almost never in the app you are editing** — proximity, not quality, is the failure. *(A phase rendered a new category of content and left it out of the **staleness set that decides what gets rebuilt**: typecheck, lint, format, the build, 46 browser assertions and two lead sittings were all green over it, and only the close's verbatim Goal re-read found it. The code carried a correct, capitalised note predicting that exact phase — in the other application.)* |
| **An ad-hoc check you wrote this turn to verify a step or a fix** | Confirm it can fail. A check that matches nothing exits `0` and reads exactly like a pass. |
| **Consuming a fan-out audit or finding report** | **Known asymmetry:** an ABSENCE claim ("X has no callers") is systematically less reliable than a presence claim. Re-verify absences. |

### Divergence — when reality disagrees with the plan

**Find your row. Do not improvise a large deviation.**

| The divergence | What to do |
|---|---|
| **The baseline rule** | **Stop and surface it.** Small surprises: note and proceed. Big ones: stop. Never quietly improvise a large cross-cutting change. |
| **Same CLASS as one the lead already ruled on** | **Apply that ruling autonomously.** Document and surface each; do not re-block. |
| **⛔ THE LEAD ASKS FOR WORK THAT BELONGS TO NO PHASE** — mid-session, outside this unit's scope | **Do it; their ask is the authorization. But GIVE IT A HOME BEFORE YOU FINISH.** Name any high-rigor trigger it touches — authorization · secrets · destructive migrations · data loss · the public edge — and say so in one line rather than silently running it in the build lane. Then **either open a phase for it or file an issue recording what shipped, what it broke, and what decision is still outstanding.** **A control whose only record is a commit message is a control nobody will find.** *(A staging gate over the public edge shipped this way: no phase doc, no issue, no acceptance record, its entire durable trace one `controls.md` line — while reddening 16 assertions in a frozen gate suite that no unit owned reconciling.)* |
| **A genuine PRODUCT/UX choice the plan left open** | Batch them and ask. A technical divergence is not a product fork. |
| **⛔ You are about to INVENT a user-facing constraint** — a new rejection, required action, validation or representation the plan did not name | **Stop.** That is a product decision, including when you are only *assigning an existing* capability, permission or role. |
| **⛔ A RECORDED FORK BLOCKS YOU** — the doc carries a "both sides carry the lead's authority, recorded not resolved" block | **Stop.** That is not yours to resolve. |
| **A locked decision CONTRADICTS ITSELF** — literal text vs its own gloss | The **invariant governs the literal rule**. Implement the invariant and surface the contradiction. |

### Keep the lead oriented

**At each step boundary emit a one-line plain-text ledger in the chat** — it is the lead's only reliable position signal. **And keep the step tracker current** (`TaskCreate` one task per step at the start, `TaskUpdate` as each lands); on a resume, only the incomplete ones matter.

**⛔ NUMBER STEPS `Phase.Step` AND NEVER INVENT A NAME FOR ONE — NO `13.2a`, NO `13.2b`, NO `13.2fixes`.** Numbering is numeric at every level. **When a step needs sub-dividing, the next level down is a `.Task` — `13.2` becomes `13.2.1`, `13.2.2`** (`AgenticEngineering_Workflow.md` §Phase / Step / Task Terminology owns this). **When work has to go *between* two steps, the new one takes the integer slot and everything after it resequences.** ⚠ **The letter suffix always feels like the cheap option mid-run, because resequencing looks expensive and a decimal looks like a promotion** — it is neither: an invented suffix is unsortable, ungreppable, and means nothing to the next agent or to the lead reading the ledger. **Tasks are AVAILABLE, not mandatory** — most steps never need one, and an ordinary step list is `19.1`…`19.5` with no third level anywhere.

**⛔ THE WRITE CEILING — one test settles every sentence: CAN THE NEXT AGENT GET THIS FROM THE CODE OR THE COMMIT? Then do not write it.** The three that keep getting written and must not: the content of a file you just edited · a narrative of how you did it · a finding whose commit message already carries it. **The execution record is a ledger — `step · commit · result · next` — not an essay.** **⚠ AND A LEDGER ROW CANNOT CARRY THE SHA OF THE COMMIT THAT CONTAINS IT.** Do not leave a `<this commit>` placeholder to fix afterwards — that buys a second commit whose entire content is a SHA. **Either write the row in the NEXT commit, or cite the step rather than the hash** (*"landed at `16.2`"*, *"the `🎉` commit"*). `git log` is authoritative for hashes; the ledger is for the reader's orientation. *(Twice in one day, on two different phases, each costing a commit.)* *(One phase's execution log ran 1,990 lines, 53% of the doc and 7× the plan it executed.)* Same test on the read side: **if you need to know how the previous agent did something, read the code, not their log entry.**

## 3) TRY — the lead uses it

**Take one cheap observable that the path is alive** — that is all the testing this stage authorises. Then **hand back a URL and the exact click path, and STOP.**

**⚠ BEFORE THE SITTING, ASK WHAT YOUR FIXTURE DISTRIBUTION MAKES IMPOSSIBLE TO SEE — and what it is showing you only by luck.** A seeded tree is not a small version of a real one; it is a **differently-shaped** one, and *empty/full*, *one/many* and *present/absent* are exactly the axes it distorts. *(Four of seven beats held no articles, so sorting on name alone put an empty one first and a reader met "Nothing has been published here yet" at the top of the page. The lopsided seed is the ONLY reason it was visible — on a realistic newsroom it would have rendered perfectly on every build and surfaced months later, on the first beat to go quiet.)* **The same distribution that reveals one defect by accident is hiding its opposite.**

**⛔ NEVER BREAK THE LEAD'S RUNNING ENVIRONMENT TO GET HERE.** Do not stop, tear down, rebuild or re-point the running stack without telling him first — never as a convenience, never silently. If a restart is genuinely needed: say so, do it fast, then **open the surface and confirm it loads and is usable.** A green gate, a healthy container and a passing build have each certified an unusable admin on this project; **only loading it proves it.**

**⛔ BEFORE YOU INVOKE AN EXISTING GATE FOR INFORMATION RATHER THAN FOR ITS VERDICT, ASK WHAT IT MUTATES.** Several gates in this repo stop containers, reseed data or rebuild images. *(Needing a cheap "is the admin reachable?" answer, a run reached for a stack gate. It tore the whole stack down — proxy, cms, migrate, db, network all removed — and rebuilt it mid-run, to answer a question a two-line probe answers.)* **A question about whether something is up is answered with the cheapest probe that answers it, never with a gate you have not read.**

**⛔ AN EXECUTOR MAY NOT MARK A `⚠human` STEP `✅`. It may only mark it `▶ SCAFFOLD COMPLETE — sitting owed`.** A headless probe over that surface is *preparation for* the sitting, **never a substitute for it**, however many assertions it carries. *(One `⚠human` step was closed `✅` on a 17-assertion agent-written browser probe, 0 failures. The Resume block still listed the sitting as owed, so the doc recorded the step done and its human gate outstanding at the same time, and ten steps landed on top. When the lead finally drove that exact surface it took **minutes** to find controls wrapping raggedly out of a fixed-width strip — and then a **data-loss** bug: clicking a transition silently discarded unsaved edits. The probe was green through both.)*

**⛔ A STEP MARKED `✅` WHOSE SITTING IS STILL LISTED AS OWED IS A CONTRADICTION — RECONCILE IT BEFORE PROCEEDING.** These two states are mutually exclusive. The contradiction was visible in the doc for two runs and nobody read it as one.

**If a `⚠human` tag DROPS** because the observable turned out genuinely machine-checkable, **say so in the ledger at the moment it drops** — so that a step still carrying the tag is known to be genuinely owed.

**⛔ A step needing a human is NOT discharged by the human ACTING — it is discharged by the ARTIFACT WORKING.** When the lead supplies a credential or clicks a button, the step closes when the thing it unblocks is observed working, not when he replies.

**Transcribe the lead's verdict into the phase doc, verbatim and attributed**, as part of discharging the step.

## 4) STRENGTHEN

**Repair what the lead's use exposed.** His findings are the work. Then loop back to Build for the next step.

**Testing — three questions, and question 1 comes first:**

1. **What existing test already covers this?**
2. **What is the cheapest observable I need while building?**
3. **Did the human test expose a regression that now deserves a test?**

**⛔ ONE REAL-PATH SMOKE IS THE ORDINARY MAXIMUM — a ceiling, not a mandate to author a gate. GATES ARE FROZEN: author no new `scripts/check-*.ts`.** If you believe question 3 genuinely requires one, **make it a numbered `⛔ YOUR CALL` item with your recommendation and let the lead rule** — do not author it and do not mention it anywhere else in the message. RED demonstrations, discriminator design and gate matrices are HIGH-RIGOR only.

**Suspend needs a NAMED blocker — a step boundary is not one.** In order of how often they actually fire *here*:

1. **The lead ends the run.** On this project that is the norm, not the exception — you are working *with* them, and the act you just walked together is the natural stopping point.
2. **Only human-gated work remains** and the lead is unavailable.
3. **Written-but-uncommitted work is at recovery risk** — commit or hand off.
4. **Context is running out** — wrap at the next cohesive boundary. **~400k is an attention ceiling, not a fraction of the window; it does not scale up on a larger session.**
